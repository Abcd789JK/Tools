# AGENTS.md — Bash 脚本开发规范

本文档是本项目 Bash Shell 脚本的强制开发规范，供开发人员和 AI Agent 在编写、修改、审查、测试及交付代码时共同遵循。适用范围包括独立 `.sh` 脚本、Bash 自动化任务、部署脚本、运维脚本，以及由 Bash 脚本加载的辅助模块。

> **核心原则：** 安全第一、正确优先、明确胜于隐式、可维护胜于炫技。脚本必须可读、可诊断、可测试、可追踪，并且在失败时尽可能保持系统和用户数据安全。

本文中的“必须”“不得”“应当”“建议”具有明确约束含义：

- **必须 / 不得：** 强制要求，不得随意违反。
- **应当：** 默认遵循；确有技术原因时，需在代码或交付说明中解释。
- **建议：** 推荐实践，可根据项目约束调整。

---

## 1. 总体开发准则

1. 默认使用 Bash，不得把 Bash 脚本当作 POSIX `sh` 执行，也不得使用 `sh script.sh` 启动 Bash 脚本。
2. 优先使用 Bash 内置功能；只有在确有必要时才使用外部命令，避免无意义的子进程、复杂管道和重复解析。
3. 代码必须清晰、直观、可维护。不得为了减少行数而压缩逻辑、滥用短变量名或写难以阅读的一行式命令。
4. 一个函数只处理一个主要职责。复杂流程必须拆分函数，并通过清晰的函数名表达意图。
5. 不得静默忽略错误。每个可能失败的关键操作都必须有明确的失败处理和合理的退出状态。
6. 默认考虑空值、空格、特殊字符、通配符、文件不存在、权限不足、网络异常、重复执行和中断退出等边界情况。
7. 不得擅自覆盖、删除或修改用户数据、系统配置、服务状态及项目文件；操作范围必须与用户要求一致。
8. 外部输入一律视为不可信数据。必须验证参数、路径、文件名、环境变量和网络返回内容。
9. 禁止提交密码、访问令牌、私钥、Cookie、数据库凭据、真实证书私钥及其他敏感信息。
10. 脚本应尽可能幂等：重复执行不应产生重复配置、重复任务或额外破坏。
11. 不得以“脚本通常由 root 执行”为由省略权限校验；root 权限也不代表可以忽略参数和路径安全。
12. 不得虚构执行结果、测试结果、Git 状态、提交记录或依赖版本。

## 2. 文件头部与脚本基本结构

### 2.1 强制文件头

每个独立、可执行的 Bash 脚本必须以以下格式开头。字段名称、排列顺序、缩进和分隔线必须保持一致：文件头上下两条分隔线均由恰好 50 个 ASCII 连字符 `-` 组成（不计行首的 `# `）；所有文件头示例必须使用相同长度。

```bash
#!/usr/bin/env bash

# --------------------------------------------------
# name   : ssl.sh
# desc   : SSL 证书管理脚本
# date   : 2026-11-03 16:00:00
# author : ChatGPT JK789
# ver    : 0.2.3
# --------------------------------------------------
```

字段填写要求：

| 字段 | 强制要求 |
| --- | --- |
| `name` | 必须填写实际脚本文件名，包含扩展名，例如 `ssl.sh`。 |
| `desc` | 用一句简洁、准确的话说明脚本主要用途，不得使用“执行相关操作”等空泛描述。 |
| `date` | 格式固定为 `YYYY-MM-DD HH:MM:SS`，填写创建时间或本次实质性修改时间，不得伪造。 |
| `author` | 默认使用项目指定的 `ChatGPT JK789`；若项目明确指定其他作者，则遵循项目设置，不得虚构身份。 |
| `ver` | 使用项目规定的稳定版三段式版本号 `主版本.次版本.修订版本`，例如 `0.2.3`；升级规则统一遵循第 20.6 节。`SCRIPT_VERSION` 的声明格式及一致性要求统一见第 20.6.14.2 节。 |

其他要求：

- Shebang 必须是第一行，前面不得有空格、空行、编码标记或其他字符。
- Shebang 后空一行，再写文件头；文件头结束后空一行，再写脚本主体。
- 不得擅自把字段改成 `Script`、`Purpose`、`Updated`、`Version` 等其他形式。
- 不得保留“脚本名字”“具体功能说明”等占位内容，正式脚本必须填写真实信息。
- 文件名变更时必须同步更新 `name` 字段。
- 修改脚本逻辑、功能或重要行为时，应更新 `date`；纯拼写修正是否更新由项目版本策略决定。
- 版本号必须与项目发布策略一致，并严格遵循第 20.6 节。若 Git 标签或项目版本文件是唯一版本来源，不得制造互相冲突的版本号。

### 2.2 独立脚本的标准启动段

本节规定紧接 2.1 文件头之后的启动代码。**文件头只以 2.1 为唯一模板来源，不得在其他章节另行定义不同版本的文件头格式。** 每个独立、可执行脚本必须按以下顺序启动：严格模式、Root 权限检查、脚本版本常量，然后才进入其他初始化和业务逻辑。

```bash
# 启用 Bash 严格模式。
set -Eeuo pipefail

# 检查并确认当前进程具备 Root 权限。
if (( EUID != 0 )); then
    printf '[ERROR] 此脚本必须以 root 权限运行。\n' >&2
    printf '请使用以下命令重新运行（已保留原有参数）：\n  sudo -- bash %q' "$0" >&2
    if (( $# > 0 )); then
        printf ' %q' "$@" >&2
    fi
    printf '\n' >&2
    exit 1
fi

# 声明当前脚本版本。
# 必须与文件头 ver 完全一致；声明格式统一见 20.6.14.2。
readonly SCRIPT_VERSION="0.2.3"

# 后续再定义其他全局常量、初始化函数、工具函数、业务函数和 main。
```

若简单脚本只保留 `SCRIPT_VERSION` 供自动化工具静态读取、运行时并不使用该常量，可能触发 ShellCheck `SC2034`；是否需要局部豁免，统一按 20.6.14.2 第 3 项处理，不得在此处另设豁免规则。

**Root 启动要求（强制）：**

本项目已明确选择统一 Root 启动策略：所有独立、可执行的 Bash 脚本均必须以 Root 身份运行，不以脚本是否实际执行特权操作作为豁免条件。不得自行以最小权限原则为由取消、延后或绕过该入口检查；任何例外都必须经过项目明确批准。

1. 所有独立、可执行的 Bash 脚本必须以 Root 身份运行；必须使用 Bash 内置变量 `EUID` 检查，不得通过 `whoami`、用户名字符串或文件权限推断。
2. Root 检查必须在任何业务逻辑和副作用之前完成，包括文件写入、安装软件、修改权限、操作服务、修改网络及其他系统状态变更。
3. 非 Root 时必须向标准错误输出明确提示，并使用非零退出码立即退出。
4. 不得默认在脚本内部调用 `sudo`、自动重新执行自身或静默切换身份；应提示用户使用 `sudo -- bash script.sh`。如需展示重运行命令，必须保留原始参数，并正确转义每个参数。
5. 即使脚本的部分功能不需要特权，仍须遵守本项目统一的 Root 启动要求。`--help`、`--version` 等参数也默认先执行 Root 检查，除非项目明确批准例外。
6. **脚本正文中的 Root 检查无法防止解释器启动前的代码执行。** 非交互 Bash 可能在读取脚本正文前执行 `BASH_ENV` 指定的文件；`#!/usr/bin/env bash` 也会在正文运行前依据 `PATH` 查找 Bash。调用方必须在提权或服务启动边界建立可信环境，审查并清理不可信的 `BASH_ENV`、`ENV`、`PATH` 及可能影响动态链接器的环境变量。不得使用 `sudo -E` / `--preserve-env` 无差别保留调用方环境。systemd、CI 等启动器必须只传入明确允许的环境变量；不得依赖脚本正文中的 `unset` 补救启动前风险。Root 运行环境的详细安全要求见第 14 节。

**库文件例外：** 被 `source` 加载的库文件不是独立可执行入口，不得在加载时直接 `exit`、执行主流程或改变调用方 Shell 的选项和 Trap。Root 检查由独立入口脚本负责；库文件中的特权函数仍必须在执行具体特权操作前验证调用条件。不得把可执行入口伪装成库文件以绕过 Root 规则。

### 2.3 文件内容组织顺序

独立脚本应按以下顺序组织，避免常量、函数和主流程散乱：

1. Shebang 与 2.1 规定的统一文件头。
2. 2.2 规定的启动段：严格模式、Root 检查和 `SCRIPT_VERSION` 声明。
3. 其他全局常量与默认配置。
4. 颜色初始化及日志函数。
5. 依赖检查、参数解析等通用辅助函数。
6. 业务函数。
7. `main()` 主入口及文件末尾的 `main "$@"` 调用；入口细节统一遵循第 8 节。

本节只规定文件的组织顺序；文件头、启动检查、版本声明和主入口的具体要求分别以 2.1、2.2、20.6.14.2 和第 8 节为准。不得在函数定义之间穿插零散的顶层业务命令，也不得在函数定义阶段执行安装、删除或其他系统修改动作。

## 3. Bash 版本、编码与格式

1. 项目必须明确最低 Bash 版本；没有既定约束时，新增脚本默认以 Bash 4.4+ 为目标。若需兼容 macOS 自带的 Bash 3.2，必须避免不兼容特性并实际验证。
2. 文件统一使用 UTF-8 编码，换行使用 LF，文件末尾必须有且只有正常的结束换行。
3. 缩进统一使用 **4 个空格**，禁止使用 Tab 缩进或混用空格与 Tab。
4. `if`、`for`、`while`、`case` 等控制结构采用统一风格：

```bash
if [[ -f "$config_file" ]]; then
    load_config "$config_file"
else
    log_error "配置文件不存在：$config_file"
    return 1
fi

for item in "${items[@]}"; do
    process_item "$item"
done

case "$action" in
    install)
        install_package
        ;;
    remove)
        remove_package
        ;;
    *)
        log_error "不支持的操作：$action"
        return 2
        ;;
esac
```

5. 优先使用 `[[ ... ]]` 进行字符串、文件和模式判断；算术判断使用 `(( ... ))`。
6. `then`、`do` 与条件表达式同行，`else`、`elif`、`fi`、`done`、`esac` 各自保持清晰的层级。
7. 长命令应按参数分行；续行反斜杠 `\` 必须是该行最后一个字符，后面不得有空格。
8. 一行只表达一个主要操作。不得将多个无关命令用分号压缩在一行。
9. 避免过深嵌套；超过三层时应考虑提前返回、拆分函数或使用 `case`。
10. 不得为了格式美观而破坏语义；格式化工具不得擅自改变脚本行为。

## 4. 命名与大小写规范（强制）

命名风格必须统一。除外部环境变量、项目明确要求的 API 名称及 Bash 固有名称外，禁止混用 camelCase、PascalCase 和随意的大写命名。

### 4.1 函数命名

**所有自定义函数名必须使用全小写 `snake_case`（小写字母加下划线）。** 这是硬性规则：

- 正确：`check_root`、`check_dependencies`、`install_package`、`create_backup`、`log_error`、`setup_colors`、`main`。
- 错误：`CheckRoot`、`checkRoot`、`CHECK_ROOT`、`check-root`、`checkroot`。
- 函数名必须以小写英文字母开头，后续仅使用小写字母、数字和下划线。
- 函数名必须表达动作或职责，优先使用动词或动宾结构，如 `validate_config`、`restart_service`。
- 禁止使用含义不明的函数名，如 `do_it`、`run1`、`test_func`、`handle`；除非 `handle` 后有清晰对象，如 `handle_signal`。
- 主入口统一命名为 `main`，不得同时定义 `Main`、`MAIN` 等不同形式。
- 由库文件暴露的函数必须使用模块前缀，避免不同模块之间的函数名冲突，例如 `ssl_load_config`、`dns_validate_record`。
- 函数名不得与 Bash 内置命令、常用外部命令或项目公共函数重名，除非确有兼容需求并有明确说明。
- 不得使用大小写变化表达函数的公私有区别；Bash 没有真正的函数访问控制。

函数声明格式、职责划分、参数和返回值约定统一见第 5 节；本节只规定命名风格，不重复展示函数实现。自定义函数必须使用 `function_name() {}` 格式，不使用 `function` 关键字。

### 4.2 变量命名

- 普通变量使用全小写 `snake_case`：`config_file`、`backup_dir`、`service_name`。
- 函数局部变量同样使用全小写 `snake_case`，并且必须使用 `local` 声明。
- 常量使用全大写 `UPPER_SNAKE_CASE`，例如 `DEFAULT_TIMEOUT`、`CONFIG_DIR`、`APP_NAME`；声明后优先使用 `readonly`。
- 环境变量遵循操作系统或外部工具原有大小写，不得随意改名；项目自定义环境变量使用有项目辨识度的全大写前缀，例如 `SSL_TOOL_DEBUG`。
- 布尔变量使用 `is_`、`has_`、`enable_`、`use_` 等前缀，例如 `is_valid`、`has_backup`、`enable_debug`。
- 数组变量仍使用小写 `snake_case`；多个元素的集合优先使用复数名，例如 `package_names`。
- 不得使用 `a`、`b`、`tmp1`、`data2` 等无语义名称；短循环变量只可用于范围极小且含义明确的场景。
- 不得覆盖 Bash 特殊变量或常见环境变量，例如 `PATH`、`HOME`、`PWD`、`OLDPWD`、`RANDOM`、`SECONDS`、`UID`、`EUID`、`IFS`、`BASH_SOURCE`。

## 5. 函数设计与编写规范

1. 函数必须职责单一，避免同时解析参数、修改配置、重启服务和输出大量日志。
2. 函数建议控制在约 50 行以内；超过 80 行时必须检查是否能拆分。复杂业务可以例外，但必须有清晰的分区和注释。
3. 函数参数通过位置参数接收，进入函数后应尽快保存到有意义的局部变量中。
4. 函数内的变量必须声明为 `local`；常量可在文件级定义为 `readonly`。
5. 函数不得依赖调用方偶然存在的变量。必要状态必须通过参数显式传入，或在模块级明确声明。
6. Bash 使用动态作用域，局部变量可能被被调函数访问；因此必须避免同名局部变量产生隐式依赖，并明确函数之间的状态传递。
7. 函数成功返回 `0`，失败返回非零值；不要把字符串当作 `return` 的返回内容。
8. 函数需要返回文本时，应清楚定义标准输出契约；日志统一写入标准错误，不能污染机器可读结果。
9. 不需要返回数据的函数，不要无意义地输出文本；不要混用 `echo`、日志和函数结果。
10. 函数内优先使用 `return`，不要随意使用 `exit` 终止整个脚本；只有脚本入口层负责最终退出。
11. 函数不得通过 `cd`、修改 `IFS`、更改 Shell 选项或安装全局 Trap 悄悄污染调用环境；确有需要时应恢复原状态。
12. 函数调用时必须传入正确参数，不得依赖未引用的 `$@` 或 `$*`。
13. 对外部可复用函数，应在函数上方写明用途、参数、返回值和副作用。

标准函数注释和实现示例：

```bash
# 检查指定命令是否已安装。
# 参数：$1... 表示一个或多个命令名称。
# 返回：全部命令均存在时返回 0；任意一个缺失时返回非 0。
check_dependencies() {
    local dependency_name

    for dependency_name in "$@"; do
        if ! command -v "$dependency_name" >/dev/null 2>&1; then
            log_error "缺少依赖：$dependency_name"
            return 1
        fi
    done
}
```

## 6. 变量、参数与引用规则

1. 默认对变量展开使用双引号，防止单词拆分和路径名展开：

```bash
printf '%s\n' "$file_path"
cp -- "$source_file" "$target_file"
```

2. 数组必须使用 Bash 数组，不得将多个参数拼成一个普通字符串：

```bash
command_args=(--recursive -- "$target_dir")
some_command "${command_args[@]}"
```

3. 遍历数组必须使用 `"${array[@]}"`，不得使用未引用的 `${array[@]}`。
4. 不得使用字符串拼接模拟命令参数列表；动态命令参数必须保存在数组中。
5. 禁止使用 `eval` 执行拼接后的字符串。任何不得不使用 `eval` 的场景都必须先论证安全性并经用户明确批准。
6. 使用 `${variable:-default}` 为可选变量提供默认值；必须存在的变量可使用 `${variable:?错误提示}`。
7. 读取用户输入时使用 `read -r`，并正确处理空输入、超时和 EOF。
8. 对文件名、路径和参数必须正确引用；对支持 `--` 的外部命令，使用 `--` 结束选项解析。
9. 参数个数和内容必须校验；缺少必需参数时输出用法说明并以非零状态退出。
10. 不得假设当前工作目录固定。需要定位脚本资源时，应基于 `${BASH_SOURCE[0]}` 计算脚本路径。
11. 不要全局修改 `IFS`。确需调整时使用局部作用域或保存并恢复原值。
12. `export` 只用于确实需要传递给子进程的变量，不得无差别导出内部变量。
13. 变量赋值与命令替换分开写，防止 `local` 掩盖命令退出状态：

```bash
local version
version="$(some_command)" || return 1
```

不要使用可能掩盖失败状态的写法：

```bash
# 不推荐：local 可能使命令替换的失败状态无法按预期传播。
local version="$(some_command)"
```

14. `printf` 的格式字符串必须是固定格式，不得把用户输入或外部数据直接作为格式参数；应使用 `printf '%s\n' "$value"`，避免格式占位符注入或意外解释反斜杠。
15. 使用 `read` 时默认采用 `IFS= read -r`；读取文件必须正确处理最后一行没有换行的情况，并明确处理 EOF。
16. 不得把会修改外层变量的 `while read` 循环直接放在管道右侧，因为管道组件通常在子 Shell 中执行，循环内变量修改可能丢失。优先使用进程替换或重定向，并按目标 Bash 版本验证；但若生产者命令的退出状态影响结果，必须单独捕获并校验，不能只依赖进程替换：

```bash
while IFS= read -r -d '' file_path; do
    file_paths+=("$file_path")
done < <(find "$search_dir" -type f -print0)
```

**进程替换的重要限制：** `< <(command)` 中的生产者异步运行，其退出状态不会自动成为 `while` 循环或外层命令的退出状态。若必须确认 `find` 等生产者成功，必须先将输出写入本次创建的临时文件并单独检查生产者退出码，再从文件读取；若使用 NUL 管道来取得生产者状态，则必须处理管道子 Shell 导致的循环变量作用域问题。不得因循环正常结束就假定生产者成功。

17. `[[ string =~ regex ]]` 中正则表达式应保存在独立变量或按 Bash 规则正确引用；不得把需要正则解释的表达式整体加引号导致匹配语义改变。
18. 命令替换会删除输出末尾的换行符；需要保留任意字节、NUL 或精确文件内容时，不得使用命令替换传输，应使用文件、文件描述符或其他二进制安全方式。
19. 外部输入不得未经校验就用于算术展开、`(( ... ))`、数组下标或动态变量名；这些上下文具有 Bash 表达式语义。接收端口、数量、时间等数字时，应先用明确的十进制正则校验，再转换和检查范围，避免把用户输入当作算术表达式执行。例如，端口应先验证 `^[0-9]{1,5}$`，再检查范围 `1..65535`；不得直接对用户原始字符串执行算术表达式。

## 7. Shell 严格模式与执行行为

所有独立、可执行脚本默认使用：

```bash
set -Eeuo pipefail
```

各选项含义：

- `-e`：符合条件的未处理命令失败时退出；其行为受条件判断、逻辑列表、管道和函数调用上下文影响。
- `-E`：使 ERR Trap 在函数、命令替换和子 Shell 环境中继承，但仍受 Bash 规则限制。
- `-u`：引用未设置变量时视为错误；可选变量必须使用 `${variable:-}` 等安全展开。
- `pipefail`：管道中任意命令失败时，管道整体返回失败状态。

严格模式不是完整错误处理机制，必须遵守以下边界：

1. 关键操作必须根据业务语义显式检查状态码。函数若在 `if`、`!`、`&&`、`||` 等抑制 `errexit` 的上下文中调用，其内部失败可能不会触发预期退出；不得把整个主流程包在 `if main; then` 或 `main || true` 中来掩盖问题。
2. 对“无匹配属于正常情况”的命令（例如 `grep` 返回 1），必须在具体分支显式区分预期结果与真实故障。
3. 避免将 `((counter++))` 作为严格模式下的独立命令，因为算术表达式的值为 0 时会返回状态 1。`((counter += 1))` 也不是对所有初始值都安全：例如 `counter=-1` 时，递增结果为 0，命令仍返回状态 1。若不希望退出状态受计算结果影响，优先使用赋值形式 `counter=$((counter + 1))`；只有能够保证算术表达式结果非零时，才将 `((...))` 作为独立命令。
4. 不得使用 `|| true` 或重定向 `/dev/null` 隐藏未知错误。确实允许某条命令失败时，必须在该命令旁说明原因并准确处理退出状态。
5. 启用 `pipefail` 后，`producer | grep -q pattern`、`producer | head` 等可能因下游提前退出而使上游收到 `SIGPIPE`。应优先改用不会提前关闭管道的处理方式，或明确识别预期的 `SIGPIPE`；不得为此全局关闭 `pipefail`。
6. `set -x` 仅允许在明确启用的调试模式中使用；跟踪输出可能泄露密码、令牌和敏感路径，必须避免记录秘密，并在调试结束后关闭。
7. 被 `source` 的库文件不得擅自启用严格模式、改变调用方 Shell 选项或覆盖调用方 Trap；严格模式由独立可执行入口负责。
8. 必须明确命令替换中的错误处理边界：普通 Bash 模式下，`$(...)` 子 Shell 默认不会继承调用方的 `errexit`；`set -E` 只影响 `ERR` Trap 的继承，不会自动启用 `inherit_errexit`。因此，不得假设 `set -e` 能捕获命令替换内部每一条失败命令。对关键命令替换必须显式检查整体退出状态；若替换内部包含多条命令，还必须检查各关键步骤，避免前序失败被后续成功命令覆盖。

   ```bash
   # 先声明局部变量，再单独检查命令替换的退出状态。
   local output
   if ! output="$(some_command)"; then
       log_error '获取数据失败'
       return 1
   fi
   ```

   不得使用 `local output="$(some_command)"` 代替上述检查，因为 `local` 内建命令本身的返回状态可能掩盖命令替换的失败状态。项目若启用 `shopt -s inherit_errexit`，必须确认目标 Bash 版本支持并测试其行为；该选项不能代替关键操作的显式错误处理。

错误码、信号处理及 ERR Trap 的具体规则统一见第 12 节；本节不重复定义通用错误处理流程。

## 8. 主入口与脚本执行流程

1. 独立脚本必须提供 `main()` 函数，主流程集中在其中。
2. `main()` 必须接收并传递命令行参数，标准入口写法为 `main "$@"`。
3. 除文件头、Shell 选项、权限检查、常量和必要初始化外，不得在顶层散落业务执行语句。
4. 通用函数必须先定义再调用；脚本最后调用 `main "$@"`。
5. 库文件只提供函数和常量，不得自动执行 `main()`。
6. 帮助文本、参数解析、依赖检查、环境检查和业务执行顺序必须清晰。

推荐基本结构：

```bash
# 定义全局常量。
readonly APP_NAME='example'

# 定义工具函数。
log_info() {
    printf '[INFO] %s\n' "$*" >&2
}

# 定义业务函数。
run_task() {
    log_info '开始执行任务'
}

# 定义主入口。
main() {
    run_task
}

main "$@"
```

## 9. 注释与文档规范（强制）

注释必须解释代码背后的**原因、约束、风险、输入输出和副作用**，不能只是把代码翻译成中文。

### 9.1 文件级注释

- 文件头字段及格式统一遵循第 2.1 节；本节不另行定义或复制文件头模板。
- 功能复杂的脚本，应在文件头之后增加“用法、依赖、权限要求、输入输出和注意事项”说明。
- 涉及系统修改、服务重启、网络调整、证书替换或数据删除的脚本，必须说明影响范围和关键风险。

### 9.2 函数级注释

公共函数、复杂函数、存在副作用的函数必须说明：

- 功能：函数做什么，以及不做什么。
- 参数：参数顺序、含义、格式、是否必需、允许值。
- 返回：成功和失败的返回状态；如果通过 stdout 输出数据，应说明输出格式。
- 副作用：是否写文件、改权限、访问网络、变更服务或修改系统状态。
- 前置条件：是否要求 Root、依赖命令或特定目录/配置。

简单且自解释的短函数无需堆砌重复注释，但函数名必须足够清晰。

### 9.3 逻辑级注释

以下情况必须添加注释：

- 复杂算法、非直观分支、特殊判断和业务规则。
- 兼容性处理、绕过方案、特殊版本限制及原因。
- 删除、覆盖、权限变更、服务重启等高风险操作。
- 临时文件、锁、信号处理、Trap 和资源清理逻辑。
- 容易被误删或误改的关键代码。

### 9.4 注释语言和格式

- 普通说明性注释统一使用完整、简洁的陈述句，以 `# ` 开头并以中文句号结束；不得混用 `# ---------- 标题 ----------` 作为代码分组标题。需要区分代码区域时，使用空行和清晰的函数/变量命名。\n- 函数注释中的“功能、参数、返回、副作用、前置条件”等字段属于结构化说明，统一使用 `# 字段：说明。` 格式；文件头元数据及 `.gitignore` 等配置文件的必要格式例外，遵循对应章节的模板。
- 默认使用简体中文注释；外部 API、协议、命令、变量名和标准术语保留原文。
- 注释必须简洁、准确、语义完整，避免错别字、口语、模糊词和无意义感叹。
- 注释必须与代码保持同步。修改代码行为时必须同步修正旧注释。
- 不得逐行注释显而易见的代码，例如 `count=1 # 将 count 设为 1`。
- 不得留下无上下文的 `TODO`、`FIXME`、`XXX`、`HACK`。必须写清原因、待办内容和适用条件；有工单时附上编号。
- 不得注释掉大段旧代码作为备份。旧实现应由 Git 历史追踪。
- 不得在注释、示例和日志中写入真实密码、令牌、私钥等敏感信息。

## 10. 终端输出、日志与颜色管理（强制）

终端输出必须统一、可读、稳定。颜色只能辅助表达状态，不能成为识别信息的唯一依据。

### 10.1 输出通道

- **标准输出 stdout：** 仅用于程序结果、供管道消费的数据、明确的最终报告或用户要求的内容。
- **标准错误 stderr：** 用于运行过程中的信息、进度、提示、警告、错误和调试输出。
- 所有 `log_*` 输出函数默认写入 stderr，避免运行信息污染 stdout 数据流。
- **脚本运行信息只输出到终端，不得由脚本自行创建、写入或追加任何持久化日志文件。** 不得设置安装日志或执行日志文件路径，不得使用 `tee`、输出重定向、`logger`、Syslog 或 journald 将本次运行内容另行保存到文件或系统日志。用户在脚本外主动使用 `> file`、`2> file` 或终端录制工具，不属于脚本自行生成日志。
- 不得把密码、Token、私钥、Cookie、授权头或完整敏感环境变量写入终端输出。
- 运行信息必须描述具体对象和问题，禁止只输出“出错了”“失败”等无效信息。

### 10.2 日志等级和固定标签

全项目统一使用以下等级，不得在同一脚本中随意混用 `INFO`、`Info`、`info` 等大小写：

| 函数 | 标签 | 颜色 | 用途 |
| --- | --- | --- | --- |
| `log_info` | `[INFO]` | 青色 | 普通信息、执行阶段 |
| `log_success` | `[ OK ]` | 绿色 | 已确认完成的操作 |
| `log_warn` | `[WARN]` | 黄色 | 非致命问题、风险提示 |
| `log_error` | `[ERROR]` | 红色 | 操作失败、错误原因 |
| `log_debug` | `[DEBUG]` | 灰色 | 仅调试模式输出 |

要求：

1. 日志函数名称必须使用全小写 `snake_case`。
2. 只有操作确实完成并验证成功后，才允许输出 `[ OK ]`；不能把“开始执行”描述为成功。
3. 警告和错误必须输出到 stderr。
4. 调试日志默认关闭，只有显式启用调试选项或环境变量时才输出。
5. 日志前缀、标签、标点和语言风格应在整个项目保持一致。

### 10.3 颜色管理原则

- 颜色代码必须集中定义和初始化，禁止在业务函数中散落 ANSI 转义序列。
- 推荐使用 ANSI 基础 8 色及必要的亮色扩展（例如 `90` 灰色/亮黑），并统一定义 Reset；不得宣称所有终端都支持完整 256 色或真彩色。
- 颜色变量统一使用全大写名称，例如 `COLOR_RED`、`COLOR_GREEN`、`COLOR_RESET`。
- 当前颜色常量同时用于 stdout 菜单和 stderr 日志时，只有 stdout 与 stderr 都是交互式终端才启用颜色（`[[ -t 1 && -t 2 ]]`）；这样任一输出流被重定向时都不会把 ANSI 控制字符写入文件或管道。若项目分别为 stdout/stderr 管理颜色，则可分别判断对应文件描述符。
- 只要 `NO_COLOR` 环境变量已设置（包括空值），就必须禁用颜色。
- 当 `TERM` 为 `dumb`、为空或未提供时，应禁用颜色；不得仅凭 `TERM` 字符串认定输出是交互式终端，仍须同时检查对应文件描述符的 TTY 状态。
- 非交互环境、CI、cron、管道和日志重定向不得强制输出 ANSI 控制字符。
- 日志颜色关闭后，标签和文字必须完整保留，不能依赖颜色传递状态。
- 不得默认使用闪烁、快速变色、全屏控制、隐藏光标等影响终端体验的效果。
- 如实现 `--no-color`，必须优先尊重该选项；颜色关闭逻辑不得被后续初始化重新覆盖。

### 10.4 统一颜色初始化和日志函数模板

颜色变量必须先初始化为空字符串，确保严格模式下不会因未定义变量而退出。所有日志输出统一写入 stderr：

```bash
# ANSI 颜色常量，由 setup_colors 根据终端环境初始化。
COLOR_RESET=''
COLOR_RED=''
COLOR_GREEN=''
COLOR_YELLOW=''
COLOR_BLUE=''
COLOR_PURPLE=''
COLOR_CYAN=''
COLOR_GRAY=''

# 根据终端能力和 NO_COLOR 设置日志颜色。
setup_colors() {
    # NO_COLOR 只要存在就禁用颜色；TERM=dumb 也不启用颜色。
    if [[ -t 1 && -t 2 && -z "${NO_COLOR+x}" && -n "${TERM:-}" && "$TERM" != 'dumb' ]]; then
        COLOR_RESET=$'\033[0m'
        COLOR_RED=$'\033[31m'
        COLOR_GREEN=$'\033[32m'
        COLOR_YELLOW=$'\033[33m'
        COLOR_BLUE=$'\033[34m'
        COLOR_PURPLE=$'\033[35m'
        COLOR_CYAN=$'\033[36m'
        COLOR_GRAY=$'\033[90m'
    fi
}

log_info() {
    printf '%s[INFO]%s %s\n' "$COLOR_CYAN" "$COLOR_RESET" "$*" >&2
}

log_success() {
    printf '%s[ OK ]%s %s\n' "$COLOR_GREEN" "$COLOR_RESET" "$*" >&2
}

log_warn() {
    printf '%s[WARN]%s %s\n' "$COLOR_YELLOW" "$COLOR_RESET" "$*" >&2
}

log_error() {
    printf '%s[ERROR]%s %s\n' "$COLOR_RED" "$COLOR_RESET" "$*" >&2
}

log_debug() {
    if [[ "${APP_DEBUG:-0}" == '1' ]]; then
        printf '%s[DEBUG]%s %s\n' "$COLOR_GRAY" "$COLOR_RESET" "$*" >&2
    fi
}
```

调用顺序必须是：Root 检查通过后，初始化颜色，再执行会调用日志函数的业务逻辑：

```bash
setup_colors
main "$@"
```

如果脚本实现 `--no-color`，应在参数解析后设置颜色开关，再执行颜色初始化。不得在日志函数中临时拼接不同颜色代码。

### 10.5 进度和交互

- 长时间任务可提供阶段进度，但不得高频刷屏。
- 非交互环境不得强制等待用户输入；应提供明确参数或安全默认行为。
- 破坏性操作必须明确展示目标和影响范围；除非用户明确授权无交互执行，否则必须确认。
- 密码输入应使用安全输入方式，避免回显、日志记录或命令行参数暴露。
- 进度条、转圈动画和光标控制仅能在交互式终端启用，且必须支持非交互降级。

### 10.6 交互式菜单、分隔线与键值输出格式（强制）

本节适用于带有交互式菜单、状态面板、安装摘要或配置摘要的终端管理脚本。当前 Tools 项目中的 `install.sh` 与 `Script/mihomo/mihomo.sh`，凡是提供交互式菜单或状态面板，必须保持相同的分隔线宽度、颜色语义、函数接口和排版节奏；后续新增同类管理脚本也必须沿用本规范。**本节不要求一次性安装脚本、直接执行型工具或简单选择脚本额外增加菜单、状态面板或交互界面。**

#### 10.6.1 固定分隔线

1. 单线和双线分隔符必须统一为 **50 个 ASCII 字符**，不得因脚本、菜单页面或开发人员不同而改变长度。
2. 单线常量名固定为 `HR`，内容为 50 个连字符 `-`；双线常量名固定为 `HR_EQ`，内容为 50 个等号 `=`。
3. 常量必须使用 `readonly` 声明，禁止在业务函数中直接重复书写分隔符。
4. 分隔线统一使用蓝色 `COLOR_BLUE`；禁用颜色时仍输出完整的 50 字符分隔线。
5. 必须通过 `hr()` 输出单线，通过 `hreq()` 输出双线；菜单不得自行拼接 ANSI 颜色码或另造长度不同的分隔线。

#### 10.6.2 统一颜色语义

新增菜单、状态面板和交互提示必须遵循下表。颜色是语义标记，不得仅为装饰而随意变色：

| 输出元素 | 颜色 | 规范 |
| --- | --- | --- |
| 单线、双线边框（`HR` / `HR_EQ`） | 蓝色 | 只用于分隔区域，不承担状态提示 |
| 页面标题、步骤序号、字段标签 | 青色 | 用于标题层级、流程标识和键名 |
| 成功状态、菜单选项序号 | 绿色 | 仅在操作确实成功或表示可选菜单序号时使用 |
| 一般信息、交互提示语 | 青色 | 例如“当前配置”“请输入选项” |
| 警告 | 黄色 | 表示非致命异常、风险或需要注意的状态 |
| 错误 | 红色 | 表示操作失败、不可继续或必须处理的问题 |
| 普通说明文字、描述、路径和值 | 默认色 | 不得把整段正文全部染色 |

具体优先级：菜单中的选项编号使用绿色；普通流程中的步骤序号使用青色。字段标签统一青色，字段值按语义决定：成功为绿色、警告为黄色、错误为红色、普通值保持默认色。颜色关闭时必须保持文字、标签和布局完整，不能依赖颜色才能理解含义。

#### 10.6.3 固定常量与输出函数

采用统一颜色初始化机制后，在全局常量区域定义分隔线，并在通用输出函数区域定义以下函数。`COLOR_BLUE`、`COLOR_CYAN` 和 `COLOR_RESET` 必须由 `setup_colors()` 初始化；颜色变量必须先初始化为空字符串，符合 10.3 至 10.4 的要求。

```bash
# 定义统一输出格式。
# 与 install.sh、mihomo.sh 保持同一套交互规范。
# 分隔线固定为 50 个可见 ASCII 字符；颜色语义统一遵循 10.6.2。
# 长度不包含 ANSI 颜色控制字符。
readonly HR="--------------------------------------------------"
readonly HR_EQ="=================================================="

# 打印单线分隔线。
hr() {
    printf '%s\n' "${COLOR_BLUE}${HR}${COLOR_RESET}"
}

# 打印双线分隔线。
hreq() {
    printf '%s\n' "${COLOR_BLUE}${HR_EQ}${COLOR_RESET}"
}

# 打印“标签: 值”行；标签统一青色，值由调用方按语义选择颜色。
# 普通值直接传入，不着色；状态值只能使用统一的 COLOR_* 常量着色。
kv() {
    local label="${1:?kv 缺少标签参数}"
    local value="${2-}"

    printf '  %s%s%s  %s\n' \
        "$COLOR_CYAN" "$label" "$COLOR_RESET" "$value"
}
```

函数使用要求：

1. `HR` 和 `HR_EQ` 必须与上例完全一致；不得修改为全角字符、Unicode 横线或不同长度的字符串。
2. `hr()`、`hreq()`、`kv()` 必须使用全小写 `snake_case`，输出到 stdout，供菜单、状态页和摘要布局使用；它们不是日志函数，不得把正常菜单内容写到 stderr。
3. `kv()` 的第一个参数是标签，第二个参数是值。普通值直接传入；状态值由调用处使用 `COLOR_GREEN`、`COLOR_YELLOW` 或 `COLOR_RED` 与 `COLOR_RESET` 包装。不得在调用处手写 ANSI 转义序列。
4. 不得把未经清理的外部响应、用户输入或配置内容当作带颜色的控制序列传入 `kv()`；普通外部值默认不着色，可能含终端控制字符的数据必须先净化或转义显示。
5. `hr()`、`hreq()`、`kv()` 只负责排版，不负责判断业务状态、不执行系统操作，也不得吞掉上游错误。
6. 页面标题、菜单选项、分区和状态摘要必须留有适当空行或分隔线，避免连续堆叠大量输出；同一页面不得混用 50 字符与其他宽度的边框。

#### 10.6.4 管理脚本终端标题与使用说明（强制）

管理脚本使用独立于非管理脚本的终端标题布局。不得将第 10.6.6 节的非管理脚本标题模板套用到管理脚本。

管理脚本的启动标题与使用说明必须遵循以下顺序：

1. 第一行输出 50 个 ASCII 等号组成的双线分隔符 `HR_EQ`。
2. 第二行输出管理脚本的中文显示名称和版本号，格式为 `中文脚本名称  v版本号`。显示名称必须根据脚本实际用途概括，不得直接使用 `.sh` 文件名、英文文件名或变量名；Loon、Surge、mihomo 等产品名、项目名和协议专有名词可保留原文。
3. 第三行输出作者信息，格式为 `作者  作者名称`；作者必须来自脚本元数据，不得虚构。
4. 第四行输出 50 个 ASCII 连字符组成的单线分隔符 `HR`。
5. 接着输出“使用说明”标题及编号说明内容。每条说明独占一行，使用统一缩进；内容应简洁、准确，说明重要行为、数据保留规则或操作注意事项。
6. 使用说明结束后输出 50 个 ASCII 连字符组成的单线分隔符 `HR`，然后再显示状态摘要或主菜单。
7. 所有分隔线必须通过 `hreq()` 或 `hr()` 输出，长度分别固定为 50 个 ASCII 字符；不得直接硬编码其他长度的分隔线。
8. 管理脚本标题、作者行、使用说明和菜单内容遵循 10.6.2 的颜色语义。关闭颜色时，文字、缩进和分隔线仍必须完整显示。

标准布局示例：

```text
==================================================
  mihomo 管理脚本  v1.5.6
  作者  ChatGPT JK789
--------------------------------------------------
  使用说明
    1. 重装或更新 mihomo 时，原有机场订阅会自动保留
    2. 添加订阅请用「配置管理」，勿直接编辑配置文件
--------------------------------------------------
```

参考实现：

```bash
print_header() {
    hreq
    printf '  %s  v%s\\n' "$SCRIPT_NAME" "$SCRIPT_VERSION"
    printf '  作者  %s\\n' "$SCRIPT_AUTHOR"
    hr
    printf '%s\\n' "${COLOR_CYAN}  使用说明${COLOR_RESET}"
    printf '    1. %s\\n' "$USAGE_NOTE_1"
    printf '    2. %s\\n' "$USAGE_NOTE_2"
    hr
}
```

`SCRIPT_NAME` 必须是根据脚本实际用途确定的简体中文显示名称，不得直接填写 `.sh` 文件名或英文文件名；产品名、项目名和协议专有名词可保留原文。`SCRIPT_VERSION`、`SCRIPT_AUTHOR` 和使用说明内容必须来自当前脚本的权威元数据或明确维护的常量。没有第二条说明时，不得输出空白编号。以上函数只负责显示标题和使用说明，不执行管理操作、不创建日志文件。

以上函数是布局示例，不代表所有脚本都必须定义 `print_header()`、`print_status()` 或 `print_menu()`。只有实际具有对应界面的管理脚本才实现这些函数；如果项目已有 `menu()`、`show_status()` 等函数，应在现有结构上统一样式，不得为套用示例而重复创建入口。

#### 10.6.5 与日志和终端能力的关系

1. `hr()`、`hreq()`、`kv()` 及菜单内容输出到 stdout；`log_info()`、`log_success()`、`log_warn()`、`log_error()` 和 `log_debug()` 继续按 10.1 至 10.4 的规定输出到 stderr。
2. 菜单颜色必须遵守 `NO_COLOR`、`TERM=dumb`、TTY 和 `--no-color` 规则；不得为了让菜单显示颜色而绕过 `setup_colors()`。
3. 非交互环境不得强制显示菜单或等待输入。管理脚本的管理操作统一通过交互式主菜单提供，不得设计或实现 `status`、`config`、`update` 等 CLI 子命令。确有自动化需求时，只能在用户明确提出后另行设计必要的命令行选项，不得以子命令形式实现。普通工具脚本仍可按实际任务使用必要的命令行参数或选项。
4. `clear`、光标控制和全屏刷新只能在交互式终端使用；清屏失败不得影响业务流程。不得用 `clear || true` 掩盖菜单之外的业务错误。
5. 菜单标题、分隔线、状态摘要和选项编号必须在不同页面保持相同风格；新增输出必须复用本节函数和颜色语义。

#### 10.6.6 非管理脚本的统一启动标题（强制）

本节适用于所有非管理类的独立、可执行 Bash 脚本，包括安装、更新、部署、维护辅助及其他工具脚本；管理脚本必须使用第 10.6.4 节规定的专用终端标题与使用说明布局，不适用本节。脚本启动并通过 Root 检查、完成必要的终端颜色初始化后，必须在执行主要业务操作前输出统一标题；标题必须是终端输出的第一组业务内容，不得先输出日志文件路径、运行日志位置或其他非必要信息。

1. 标题使用第 10.6.1 节规定的 50 字符双线分隔符 `HR_EQ`，不得另设宽度或自行拼接不同长度的边框。
2. 第一行显示脚本的中文显示名称和版本号，格式为 `中文脚本名称  v版本号`；显示名称必须根据脚本实际用途概括，不得直接使用 `.sh` 文件名、英文文件名或变量名。产品名、项目名和协议专有名词（如 Loon、Surge、Cloudflare DNS）可保留原文。显示名称和版本号必须来自当前脚本的权威元数据，不得在多个位置分别硬编码。
3. 所有非管理脚本都必须在脚本名称和版本号之后显示一行简明的脚本用途说明，包括安装脚本和部署脚本。说明应准确概括脚本用途、适用场景或关键限制，不得编造功能或堆砌无关信息。说明应来自当前脚本的权威元数据，并保持简洁，避免在标题中展开完整使用文档。
4. 标题中不得显示安装目录、部署目录、脚本所在目录、当前工作目录或其他文件系统路径；不得为了展示路径而增加目录元数据。
5. 标题必须使用统一颜色语义：前后双线分隔符使用蓝色 `COLOR_BLUE`，脚本名称和版本号使用青色 `COLOR_CYAN`，用途说明使用默认终端颜色；颜色必须通过 `setup_colors()` 初始化的颜色常量实现，禁止手写 ANSI 转义序列。禁用颜色时仍必须完整显示文字和分隔线。
6. 管理脚本必须使用第 10.6.4 节规定的专用终端标题与使用说明布局，不得套用本节的非管理脚本标题格式。
7. 非管理脚本不得在标题中显示日志文件路径，也不得生成安装日志、执行日志或其他持久化运行日志；运行信息只按 10.1 至 10.4 输出到终端。
8. 标题每一行（包括行首缩进）的终端显示宽度不得超过 50 列；缩进必须计入宽度，脚本名称行的可用正文宽度为 48 列，用途说明行的可用正文宽度为 46 列。超出时必须自动换行，不得因内容过长而改变 50 字符分隔线的长度。
9. 自动换行必须按 Unicode 终端显示宽度计算，正确处理中文等全角字符、组合字符及多字节字符；不得用 UTF-8 字节数或 Bash 字符串长度直接代替显示宽度，也不得截断字符或丢失内容。
10. 脚本名称及版本号行以两个空格缩进；用途说明首行必须比脚本名称行多缩进两个空格，即使用四个空格缩进。用途说明换行后的续行也必须保持四个空格缩进。脚本名称行如需换行，续行应与该行正文起始位置对齐。
11. 自动换行应优先在空格、标点或语义边界处断行，不得随意拆开英文单词、产品名称或协议名称；若单个不可拆分内容本身超过可用宽度，必须采用不会丢失字符或改变原意的安全断行方式。标题不得包含文件系统路径。

标准输出示例（安装脚本）：

```text
==================================================
  mihomo 一键安装脚本  v2.1.0
  安装并配置 mihomo 核心服务
==================================================
```

标准输出示例（非安装脚本）：

```text
==================================================
  Cloudflare DNS 证书申请脚本  v0.2.3
    仅支持 DNS-01 验证，适用于未开放 80/443 端口的家庭服务器
==================================================
```

标准输出示例（用途说明过长时自动换行）：

```text
==================================================
  GitHub 仓库自动同步备份脚本  v0.3.0
    批量拉取 GitHub 仓库更新，有更新时打包
    指定仓库目录（排除 .git）并通过 Telegram
    通知同步与备份结果
```

脚本文件名与标题显示名称示例：文件名为 `convert.sh`，用途说明为“批量将 Loon 插件转换为 Surge 模块，支持多 JSON 订阅源、并发与增量转换”时，标题名称应使用中文用途名称，例如 `Loon 插件转 Surge 模块脚本`，不得显示为 `convert.sh`。

参考实现：

```bash
print_script_header() {
    hreq
    # print_wrapped_text 按终端显示列宽换行，不得按字节数截断 UTF-8 文本。
    print_wrapped_text 2 "$COLOR_CYAN" "$SCRIPT_NAME  v$SCRIPT_VERSION"
    print_wrapped_text 4 '' "$SCRIPT_DESCRIPTION"
    hreq
}
```

`print_wrapped_text` 是标题排版辅助函数，必须在当前脚本中定义，或从项目内可信的公共库加载；调用前必须确保函数已定义，禁止留下未实现的占位调用。实现必须按 50 列边框计算可用显示宽度，将缩进计入总宽度，并按传入的缩进值输出；颜色参数为空字符串时使用默认终端颜色。实现必须正确计算 Unicode 终端显示宽度，遵循本节的语义边界换行要求，不得使用 Bash 字符串长度或字节截断代替显示宽度计算，也不得拆坏中文、多字节字符或组合字符。若实现依赖外部命令、语言运行时或库，必须将其列入依赖检查并验证目标环境可用；不得假设目标系统默认安装了特定 Unicode 宽度工具。

`SCRIPT_NAME`、`SCRIPT_VERSION` 和 `SCRIPT_DESCRIPTION` 必须在调用前完成可信赋值；`SCRIPT_NAME` 必须是根据实际用途确定的简体中文显示名称，不得直接使用脚本文件名（例如 `convert.sh`）；所有非管理脚本都必须定义 `SCRIPT_DESCRIPTION`。标题函数不得读取或显示 `INSTALL_DIR`，也不得为标题展示而额外定义安装目录或部署目录变量。该函数只负责显示标题，不创建目录、不写入文件、不执行主要业务操作，也不生成日志。管理脚本不调用该函数。

## 11. 命令行参数与帮助信息

1. 参数必须有明确语义、格式和错误提示。
2. 简单短选项优先使用 Bash 内置 `getopts`；长选项如 `--config`、`--force` 应通过清晰的 `case` 解析。
3. 参数解析必须正确处理空格、以 `-` 开头的参数、缺失值、重复选项和未知选项。
4. 必须为复杂脚本提供 `usage()` 或 `show_help()`，说明用法、参数、默认值、依赖、权限和示例。
5. 帮助文本应与实际参数保持一致，修改 CLI 后必须同步更新帮助说明和测试。
6. 不得默默忽略未知参数或错误参数。
7. 对可能改变系统状态的选项，名称必须明确，例如 `--remove`、`--force`、`--dry-run`；不得用含糊参数触发破坏性动作。
8. `--dry-run` 应只展示计划操作，不得偷偷执行真实写入或服务操作。

## 12. 错误处理、退出码与信号

本节规定错误信息、退出状态和信号处理；`set -Eeuo pipefail`、`set -e`、`pipefail` 及其控制流边界统一遵循第 7 节，不在此重复。

1. 成功返回 `0`，失败返回非零值。常见约定：`1` 通用错误、`2` 参数错误、`126` 无法执行、`127` 命令不存在；项目已有退出码规范时优先遵循。
2. 错误信息必须说明失败的操作、涉及的对象和可行的排查方向；不得只输出“出错了”“失败”等无效信息。
3. 函数应返回可由调用方判断的状态码；脚本入口负责将最终状态转换为进程退出码，不得在普通辅助函数中随意 `exit`。
4. 对 `INT`、`TERM`、`HUP` 等信号，应按资源情况设置清理机制；清理逻辑必须安全、可重复，并遵循第 13 节的资源所有权要求。
5. `ERR` Trap 不是万能机制，不得用它代替关键命令的显式状态检查。若使用错误 Trap，应避免输出可能包含敏感内容的完整 `BASH_COMMAND`。
6. 日志、错误信息和调试输出的秘密保护统一遵循第 10.1 节和第 21 节；网络超时、HTTP 状态及下载失败处理统一遵循第 15 节。

若使用错误 Trap，可采用以下不泄露完整命令内容的形式：

```bash
on_error() {
    local exit_code="$1"
    local line_number="$2"

    log_error "脚本执行失败，行号：${line_number}，退出码：${exit_code}"
    exit "$exit_code"
}

trap 'on_error "$?" "$LINENO"' ERR
```

## 13. 文件、目录与临时资源管理

本节规定正式脚本运行期间创建和管理的文件与资源；仅为调试、验证或测试创建的一次性产物，统一按第 19.3.1 节执行。本节与 19.3.1 的区分依据是资源用途，而不是文件类型。

1. 对文件进行读写前，必须确认路径、目标对象、权限、覆盖策略和影响范围。
2. 不得解析 `ls` 输出作为文件列表；应使用 Bash glob 或 `find`。
3. 遍历可能包含空格、换行或特殊字符的文件名时，必须使用 NUL 分隔，例如 `find -print0` 配合 `read -r -d ''`。
4. 不得使用固定名称创建临时文件或临时目录；应使用 `mktemp`，并设置合理权限（敏感数据建议 `umask 077`）。
5. 临时文件、目录、锁文件必须有明确生命周期，并在正常结束和异常中断时清理。
6. 清理操作必须限制在脚本自己创建的资源范围内；不得用不受控的变量执行 `rm -rf`。
7. 重要配置文件优先采用“生成临时文件—验证—备份—原子替换—验证结果”的更新流程。
8. 不得对符号链接、挂载点、设备文件和用户指定路径做未经验证的递归操作。
9. 对必须单实例运行的脚本，应使用可靠锁机制，明确锁文件位置、获取失败行为和释放规则。
10. 对目录权限、属主和文件模式进行修改时，必须明确目标范围，不得使用过宽的权限（如无理由的 `777`）。

## 14. 系统管理、Root 与高风险操作

本项目独立脚本统一要求 Root 启动，但必须遵循最小影响原则：

- Root 身份检查及解释器启动前的环境信任边界统一遵循第 2.2 节；本节不重复定义启动模板。
- Root 运行环境中的 `PATH`、`HOME`、`TMPDIR`、`XDG_*` 等变量不得默认视为可信；尤其不得让当前目录、空路径项或用户可写目录参与高权限命令搜索。执行高风险系统命令前，应确认命令解析路径可信；必要时使用受信任的绝对路径或经过验证的安全 PATH。不得为了“安全”而在不了解目标发行版的情况下粗暴覆盖整个环境。
- Root 进程创建临时文件时，不得直接信任调用方提供的 `TMPDIR`。应使用经验证、权限安全的系统临时目录，确保父目录不能被非特权用户任意替换临时子目录；临时文件/目录仍须通过 `mktemp` 创建并设置最小权限。
- Root 进程执行下载或访问 API 时，必须审查 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY`、`CURL_CA_BUNDLE`、`SSL_CERT_FILE` 和 `SSL_CERT_DIR` 等可能改变网络出口或 TLS 信任链的环境变量。业务确实需要受信任代理或自定义 CA 时，应显式允许并验证其来源；不得无条件清除合法企业代理，也不得盲目继承普通用户可控的代理 URL、代理凭据或自定义 CA。代理 URL 中的认证信息不得写入日志。
- 安装、卸载、删除、覆盖、格式化、分区、网络修改、防火墙变更、用户管理和服务启停必须检查目标对象。
- 删除或覆盖操作必须限定路径；禁止对未经验证的变量执行递归删除。
- 操作系统配置前应检查现有配置并按需备份；写入后应验证配置有效性。
- 修改服务配置后，优先执行服务自身提供的配置检查命令，再重载或重启服务。
- 能用 reload 时不得无理由使用 restart；必须考虑业务中断影响。
- 对不可逆操作必须提供预览、确认或 dry-run；需求不明确时必须停止并向用户说明。
- 不得为了“修复成功”擅自关闭防火墙、SELinux、AppArmor、TLS 校验或系统安全策略。

## 15. 外部命令、依赖与网络操作

1. 使用外部命令前，应检查命令是否存在；依赖检查应集中管理，避免散落重复检查。
2. 使用常见、稳定、明确的命令参数；注意 GNU/Linux 与 BSD/macOS 命令选项差异。
3. 不得假设 `sed`、`grep`、`date`、`readlink`、`stat`、`find` 等命令在所有系统上的选项完全一致。
4. 简单字符串处理优先使用 Bash 参数展开；复杂结构化数据必须使用合适解析工具。
5. 解析 JSON 应优先使用 `jq`；解析 YAML 应使用可靠 YAML 解析工具；不得通过脆弱正则表达式模拟完整解析器。
6. 网络请求必须设置连接超时、总超时和失败处理；下载内容应检查来源、状态码和完整性。
7. 禁止未经验证就执行远程脚本，例如 `curl URL | bash` 或 `wget -O- URL | sh`。
8. 禁止为了绕过证书错误而使用 `curl -k`、`--insecure` 等关闭 TLS 校验的参数，除非是经用户明确批准的受控诊断场景。
9. 依赖必须说明用途和必要版本；不得无理由新增大型依赖。
10. 使用 `printf` 输出格式化文本；不要依赖 `echo -e` 的实现差异。
11. 避免无意义地重复调用 `cat`、`grep`、`cut`、`awk`、`sed`，但不得为了减少进程而牺牲可读性或正确性。
12. `source` / `.` 会在当前 Shell 中执行目标文件代码，不是普通的配置读取方式。只允许加载项目内明确受信任、受版本控制或经过来源验证的 Shell 模块；不得 `source` 用户可随意编辑、从网络下载、来自临时目录或包含不可信输入的配置文件。普通配置应使用 JSON/YAML/TOML 等解析器读取，不得通过执行配置来解析数据。若项目确实必须读取 Shell 风格配置，必须明确其等同于执行代码，限制文件所有者和权限，并在信任边界处进行审核。
13. 使用 `source` 加载模块时，必须基于脚本实际路径构造受控路径，检查文件存在性和预期位置；禁止让未验证的环境变量、当前工作目录或用户输入决定高权限代码的加载路径。
14. `curl` / `wget` 跟随重定向时，必须确认重定向协议和目标主机在允许范围内；仅限制为 HTTPS 不代表目标主机可信。对于固定 API 可禁用不必要重定向；对于发布资产下载，应明确允许的资产域名并校验最终 URL。
15. 解压 ZIP/TAR 等归档文件前，必须检查归档条目；拒绝绝对路径、包含 `..` 的路径、越界符号链接/硬链接、设备文件和非预期文件类型。解压目录必须是本次创建的临时目录，禁止直接解压到系统目录或正式安装目录。
16. 下载的校验和只有在其来源可信时才有意义。若制品与校验文件来自同一可能被同时篡改的渠道，单纯 SHA-256 不能证明发布者身份；优先验证签名、签名清单、可信 Release Attestation 或独立可信渠道，并清楚说明信任模型。

## 16. 可移植性与运行环境

本节聚焦目标平台和运行环境差异：最低 Bash 版本及语法兼容性遵循第 3 节；Bash 解释器和启动方式遵循第 1 节，不在此重复。

1. 明确脚本支持的操作系统、发行版和 CPU 架构；不支持的平台必须给出明确提示并安全退出。
2. 需要访问脚本同目录资源时，应正确解析 `${BASH_SOURCE[0]}`；若涉及符号链接，必须明确是否跟随链接解析。
3. 不得假设当前工作目录、用户的 `PATH`、语言环境、时区或终端一定存在。
4. 对依赖 GNU 扩展的命令，应检查平台或明确声明 Linux/GNU 环境要求；不得假设 GNU 与 BSD/macOS 命令选项完全一致。
5. Locale 会影响排序、大小写、数字或日期解析时，应明确设置或验证环境。
6. 定时任务、服务和 CI 环境可能没有 TTY、交互输入或完整环境变量；脚本必须提供明确的非交互行为和退出状态。

### 16.1 时间与时区管理

#### 时间获取与格式

1. 获取当前系统时间统一使用 `date` 命令；获取 UTC 时间必须明确使用 `date -u`。
2. 不得假设系统时区一定是 UTC，也不得擅自修改系统时区；不得使用硬编码时间代替动态获取的当前时间。
3. 同一业务流程中应尽量统一时间来源，避免多次获取当前时间造成前后不一致。
4. 文件头部的 `date` 字段继续使用 `YYYY-MM-DD HH:MM:SS`，按创建或实质性修改时执行环境的系统本地时间填写；不得不加约定地把 UTC 时间写入该字段，也不得为该字段擅自追加时区后缀。需要跨环境审计时，可在发布元数据或变更记录中另行记录带明确时区的时间。
5. 面向用户展示的时间默认使用系统本地时间；跨系统传输或持久化存储的时间必须明确时区，优先使用 ISO 8601 格式。
6. UTC 时间统一使用 `YYYY-MM-DDTHH:MM:SSZ`；带时区偏移的时间必须保留偏移信息，例如 `2026-11-04T16:09:00+08:00`。
7. 不得混用本地时间和 UTC 时间进行比较或计算。

#### 时间计算与比较

1. 时间点比较、过期判断和有效期计算，优先转换为 Unix 时间戳后进行数值比较。
2. 不得直接对不同格式的日期字符串进行大小比较。
3. 计算时间差时，必须区分时间点与时间间隔。
4. 测量超时、等待时长和执行耗时时，必须优先使用单调递增时钟，避免系统时间被 NTP 或人工调整后影响结果。Bash 没有可跨平台直接依赖的单调时钟内建接口；需要严格计时时，必须使用目标环境中已存在且经过验证的单调计时能力。不得使用 `date` 等墙上时钟代替单调时钟，也不得仅凭连续读取系统时间实现严格超时。
5. 不得通过简单增加或减少固定秒数实现跨时区日期转换。

#### 时区、夏令时与定时任务

1. 处理指定地区的时间时，必须明确使用对应时区，不得把系统本地时区默认为某个固定时区。
2. 处理夏令时切换时，必须考虑重复出现和不存在的本地时间。
3. 定时任务涉及特定地区时间时，必须明确时区及执行时间语义；同时考虑任务延迟、重复触发和执行中断。
4. cron、systemd timer 等定时机制必须确认其执行环境的时区影响。
5. 不得通过修改系统时区来满足单个脚本的时间处理需求。

#### 超时与异常处理

1. 网络请求、进程等待、锁等待等操作必须根据实际场景设置合理超时；重试必须设置次数或总时长上限，不得无限重试。
2. 使用 `sleep` 时必须确保等待时间合理，避免无意义的长时间阻塞。
3. 必须检查时间解析和转换结果，正确处理无效日期、空时间戳及格式错误。
4. 涉及证书有效期、订阅有效期和过期判断时，必须正确处理时区和边界时间。
5. 对证书、签名、订阅、令牌等依赖系统时钟进行有效期或安全性判断的操作，如果系统时间与可信时间基准的偏差足以影响判断，必须停止相关关键操作并明确报告原因；不得因此无差别阻断与时间判断无关的其他业务。
6. 不得将远程服务器返回的时间直接视为可信的本地系统时间。

#### 命令兼容性

1. 使用 `date` 的扩展参数前，必须确认目标系统支持。
2. 不得默认 GNU `date` 与 BSD `date` 的参数完全兼容；脚本明确限定 Linux 环境时，可按目标发行版使用对应实现。
3. 不得仅为时间格式化引入不必要的外部依赖。

## 17. 性能与可维护性

1. 优先优化正确性和可维护性，不得为微小性能收益制造难以理解的代码。
2. 大量文件操作时，应避免逐个启动昂贵的外部进程；可以批量处理，但必须保留特殊字符处理和明确的失败状态。
3. 避免不必要的命令替换和子 Shell；同时不得为了减少进程而使用不安全的字符串解析或牺牲可读性。
4. 全局扫描、递归搜索和大范围通配必须有明确必要性并限制作用范围。

## 19. 测试规范与质量门禁（强制）

**每次代码、脚本、配置或文档改动后，都必须编写或更新相关测试/验证项；交付前所有适用测试和验证必须通过。** 不得只凭代码阅读或语法检查宣称正确。

### 19.1 修改前

- 阅读项目现有测试、CI 工作流、质量门禁和测试说明。
- 优先使用项目现有测试框架，不得擅自替换测试框架。
- 确认脚本会触碰的文件、服务、网络和系统资源，制定安全测试范围。

### 19.2 ShellCheck 静态分析（强制）

**所有新增、修改或受本次改动影响的 Bash 脚本，都必须通过 ShellCheck 检查。** 这项要求适用于独立 `.sh` 脚本、无扩展名但使用 Bash 的可执行文件、Bash 库文件、被 `source` 加载的模块，以及项目实际维护的 Bash 自动化脚本。不得因为脚本很短、暂时不执行、只在本机运行或没有新增功能而跳过。

ShellCheck 是静态分析工具，负责发现常见语法、语义、兼容性和可维护性问题；它不能替代 `bash -n`、Bats 行为测试或真实运行验证。ShellCheck 的官方项目说明和命令参数以其上游文档为准：<https://github.com/koalaman/shellcheck>。

#### 19.2.1 检查前的准备

1. 修改前必须检查项目是否已有 `.shellcheckrc`、`shellcheckrc`、CI 检查步骤、版本锁定文件和豁免注释；必须沿用项目已有配置，不得擅自降低检查严格程度。
2. 必须先确认 ShellCheck 可执行文件可用，并记录其实际版本：

   ```bash
   command -v shellcheck
   shellcheck --version
   ```

3. Windows PowerShell 环境必须使用 `Get-Command` 检查命令解析结果：

   ```powershell
   Get-Command shellcheck -ErrorAction Stop
   shellcheck --version
   ```

4. 不得仅凭软件包管理器显示“已安装”就认定工具可用；必须实际执行 `shellcheck --version`。若安装刚完成但当前终端仍找不到命令，应先重新打开终端，或仅刷新当前进程的 PATH，再次验证。
5. 若命令指向多个不同版本，必须明确本次实际调用的是哪一个可执行文件，避免本机、CI 和容器使用不同版本造成结果不一致。

#### 19.2.2 ShellCheck 缺失时的安装处理

检查工具不可用时，不得直接跳过，也不得将其标记为通过。AI Agent 必须按以下顺序处理：

1. 识别当前操作系统、Shell、包管理器及当前用户权限。
2. 在当前环境允许联网、安装依赖且不会违反用户授权或执行环境限制时，优先使用该环境的官方包管理器安装 ShellCheck。
3. Windows 11 优先使用 WinGet：

   ```powershell
   winget install --id koalaman.shellcheck --exact --source winget
   ```

   安装后应重新打开 PowerShell，再执行 `Get-Command shellcheck` 和 `shellcheck --version`。若当前终端需要立即使用，可刷新当前进程的 PATH：

   ```powershell
   $env:Path = @(
       [Environment]::GetEnvironmentVariable('Path', 'Machine'),
       [Environment]::GetEnvironmentVariable('Path', 'User')
   ) -join ';'

   Get-Command shellcheck -ErrorAction Stop
   shellcheck --version
   ```

   若 WinGet 不可用，可使用项目批准的 Windows 包管理器，或从 ShellCheck 官方 GitHub Releases 下载对应 Windows 预编译包。下载后必须验证包来源和校验值，并确认 `shellcheck.exe --version` 正常。
4. Debian / Ubuntu 可使用 `sudo apt-get update` 和 `sudo apt-get install shellcheck`；Fedora 可使用 `sudo dnf install ShellCheck`；Arch Linux 可使用 `sudo pacman -S shellcheck`；macOS Homebrew 可使用 `brew install shellcheck`。其他系统必须查阅对应系统及 ShellCheck 上游的安装说明，不得猜测包名或下载来源。
5. 不得使用来源不明的二进制文件，不得通过未经审查的 `curl ... | sh`、`wget ... | bash` 等方式安装；不得关闭 TLS 证书校验。
6. 不得为了安装工具擅自修改用户全局 PATH、全局 Shell 配置、全局 Git 配置或系统策略。需要管理员权限、交互式许可、接受协议或修改系统设置时，应遵守当前环境授权要求；未经授权不得绕过限制。
7. 安装后必须重新执行 `shellcheck --version`。安装失败、网络不可用、没有权限或环境不允许安装时，必须明确报告“ShellCheck 未执行”，说明原因和影响；不得伪造版本、输出或通过状态。

#### 19.2.3 版本一致性与项目配置

1. 项目应在开发说明或 CI 中明确 ShellCheck 版本要求；CI 必须固定到明确版本，不得无审查地跟随不确定的 `latest` 或每日构建版本。
2. 本地开发环境应尽量使用与 CI 相同的 ShellCheck 版本。升级版本属于工具链变更，必须审查新增告警、更新测试并单独提交。
3. 项目可在根目录使用 `.shellcheckrc` 统一配置。仅在该项目确实全部以 Bash 为目标时，才可使用以下基础配置：

   ```ini
   shell=bash
   severity=style
   ```

4. `severity=style` 表示纳入所有严重级别的检查；不得为了减少告警而将严重级别从 `style` 降为 `info`、`warning` 或 `error`。若已有经审查的项目基线，必须说明其原因和覆盖范围。
5. `.shellcheckrc` 应纳入 Git 版本管理。个人目录下的配置不得成为项目唯一的质量规则；CI 应能在干净环境中复现项目检查结果。
6. 若项目同时包含 Bash、POSIX `sh`、Dash 或其他 Shell 脚本，必须按文件实际解释器分别检查，不得对非 Bash 文件强制使用 Bash 方言，也不得把 Bash 脚本误按 POSIX `sh` 检查。

#### 19.2.4 标准检查命令

每个 Bash 脚本至少执行以下检查：

```bash
bash -n ./script.sh
shellcheck --shell=bash --severity=style ./script.sh
```

说明：

- `bash -n` 检查 Bash 语法；ShellCheck 检查静态问题，两者必须分别执行。
- 对于 Shebang 不完整、没有 Shebang 的库文件或无法自动识别解释器的文件，必须显式指定 `--shell=bash`。
- 如果脚本使用 `source` / `.` 加载项目内其他文件，应把相关库文件一并纳入检查；必要时使用 `--external-sources` 或 `-x`，并正确配置来源路径。只有在信任并确认来源范围后才允许跟踪外部来源。
- 检查多个文件时，必须正确处理空格和特殊字符，不得通过未经引用的通配字符串或 `ls` 输出拼接文件列表。
- 本次改动影响公共函数、公共库或脚本调用关系时，必须同时检查所有受影响调用方，不能只检查被编辑的单个文件。

#### 19.2.5 检查范围与排除规则

1. 必须检查所有本次新增、修改和受影响的 Bash 文件；项目具备完整脚本清单或 CI 全量检查时，必须执行项目规定的全量检查。
2. 不得仅因文件没有 `.sh` 扩展名就排除；应识别 Bash Shebang、执行入口、被加载关系和项目脚本清单。
3. 第三方 vendored 文件、生成文件或明确不归本项目维护的内容，可以按项目书面规则排除；排除项必须限定具体目录或文件，并说明来源、原因和维护责任。
4. 不得默认排除 `scripts/`、`bin/`、`lib/`、`hooks/`、`.github/` 等项目目录；不得因为文件历史遗留告警较多而直接排除整个目录。
5. 新增或修改文件不得通过把文件移动到排除目录、重命名扩展名或调整扫描范围来规避检查。

#### 19.2.6 告警修复与豁免要求

1. ShellCheck 报告的问题必须修复，并重新执行检查，直到通过。
2. 修复时必须理解告警对应的实际语义，不得只为消除提示而改变脚本原有行为、兼容性、参数边界或安全属性。
3. 不得删除功能、弱化输入校验、改用不安全变量展开、吞掉退出码或改变业务逻辑来消除告警。
4. 只有在确认告警不适用于当前代码、修复会破坏明确要求，或存在可证明的兼容性约束时，才允许豁免。豁免必须满足：
   - 精确指定 ShellCheck 编号，例如 `SC####`，不得使用 `disable=all` 或大范围编号段；
   - 在告警对应代码附近添加 `# shellcheck disable=SC####`；
   - 注释必须说明为什么该告警在此处不适用、为何不能采用常规修复，以及采取了什么风险控制；
   - 豁免范围必须尽可能限制在单条命令，不得无理由扩大到整个文件或目录；
   - 变更审查时必须重新确认该豁免仍然必要。
5. 对 `source` 路径无法解析等项目结构问题，应优先通过修正路径、配置来源目录或添加准确的 `shellcheck source=...` 注释解决；不得把真实依赖问题简单屏蔽。
6. 禁止未经审查增加全局 `disable`、`exclude`、`SHELLCHECK_OPTS` 或 CI 忽略规则；不得以“告警太多”为理由批量豁免。
7. 每一个保留的豁免，都必须在最终交付说明中列出编号、文件位置和理由；没有豁免时应明确报告“无新增豁免”。

#### 19.2.7 ShellCheck 退出码与失败判定

ShellCheck 的退出码必须按真实结果判定，不得只看终端是否打印文本：

| 退出码 | 含义 | 处理要求 |
| --- | --- | --- |
| `0` | 文件已成功检查，且没有发现问题 | 可以记录为通过。 |
| `1` | 文件已成功检查，但发现问题 | 必须修复或按规则豁免，然后重跑。 |
| `2` | 有文件无法处理，例如文件不存在或读取失败 | 检查路径、权限和文件状态，修复后重跑。 |
| `3` | ShellCheck 调用语法或参数错误 | 修正命令或配置后重跑。 |
| `4` | 格式化器或选项等调用配置错误 | 修正工具参数或配置后重跑。 |

任何非 `0` 退出码都不得标记为 ShellCheck 通过。通过管道输出日志时，必须保留 ShellCheck 的真实退出码；Bash 脚本应启用 `pipefail` 或采用其他可靠方式获取原始退出状态。禁止使用 `|| true`、`continue-on-error`、`|| exit 0` 或其他方式掩盖失败。

#### 19.2.8 CI / GitHub Actions 强制要求

1. Pull Request、合并请求和正式交付所依赖的 CI 必须执行 ShellCheck；静态检查失败必须使对应 Job / Workflow 失败。
2. CI 必须明确安装或调用固定版本的 ShellCheck，并打印版本信息；不得依赖 Runner 恰好预装的未知版本。
3. CI 检查范围必须覆盖项目全部受维护的 Bash 文件，或者有明确、可验证的增量检查策略；不得只扫描少量示例脚本。
4. 禁止对 ShellCheck 步骤设置 `continue-on-error: true`，禁止把失败步骤标记为非阻断，也禁止通过 `|| true` 吞掉退出码。
5. CI 的 `.shellcheckrc`、扫描范围、豁免规则和本地项目配置必须一致；如有差异，必须在项目文档中明确说明。
6. 修改 ShellCheck 版本、配置或扫描范围时，必须审查 CI 结果并提交对应变更，不得只在本机临时调整。

#### 19.2.9 Windows 11 特别要求

1. Windows 11 可使用原生 `shellcheck.exe`；安装、PowerShell 命令解析验证和 PATH 刷新统一遵循 19.2.1、19.2.2，不在本节重复维护安装步骤。
2. PowerShell 执行 `.sh` 静态检查时，应将文件完整路径作为独立参数传入；不能用字符串拼接命令，也不能让空格路径被拆成多个参数。
3. Windows 原生 ShellCheck 只负责静态分析，不代表 Bash 脚本已经在 Windows 原生环境运行通过。需要执行 Bash 行为测试时，必须使用项目支持的 Git Bash、WSL、容器或 Linux CI，并明确报告实际测试环境。
4. Git Bash、WSL 和 Windows PowerShell 可能拥有不同 PATH 和不同 ShellCheck 安装实例；必须在实际执行检查的环境中验证版本，不能用 Windows 主机上的版本证明 WSL 内也已安装。

#### 19.2.10 检查报告与交付标准

每次 Bash 脚本变更的交付说明必须报告：

1. ShellCheck 是否实际执行；未执行时必须明确写明原因。
2. ShellCheck 完整版本号和实际执行环境（例如 Windows 11 PowerShell、WSL Ubuntu、Linux CI）。
3. 实际执行的命令和覆盖的文件范围或文件数量。
4. 检查结果：通过、失败或未执行；不得混用这些状态。
5. 是否存在豁免；存在时列出编号、文件位置和理由。
6. 若 CI 负责最终检查，必须报告对应 Job 的真实结果；本地通过不能替代尚未运行的 CI。

**ShellCheck 未安装、无法调用、执行失败、扫描范围不完整或结果未确认时，本次 ShellCheck 状态一律为“未通过 / 未完成”，不得交付为全部验证通过。**

### 19.3 自动化测试

- Bash 行为测试优先沿用项目现有框架；没有测试框架时，可评估使用 Bats Core。
- 测试应覆盖正常路径、异常路径、参数错误、缺失依赖、空输入、文件不存在、权限不足和重复执行。
- Bug 修复必须尽可能增加能够复现旧问题的回归测试。
- 涉及 Root 的脚本，必须在隔离环境分别验证 Root 成功路径和非 Root 拒绝路径；不得为测试而删除正式权限检查。测试驱动和 Bats 测试文件应按测试所需的最小权限运行，不得因为被测程序要求 Root，就默认以 Root 运行整个测试套件；应在测试用例中分别以受控的 Root / 非 Root 身份调用被测入口。
- Bats 测试文件、测试框架和仅供测试加载的辅助模块，不因其测试对象有 Root 要求而自动成为需要 Root 启动的产品入口。只有作为项目正式产品分发的独立可执行测试工具，才按第 2.2 节判断其启动权限。
- 涉及文件修改、删除、服务或系统配置的脚本，必须优先使用临时目录、容器、虚拟机、Mock 或 dry-run 测试，不得直接拿用户生产环境做实验。
- 测试必须验证结果和副作用，不得只断言命令执行过。
- 测试不得依赖真实密码、真实外部账户或不可控的生产服务。
- 每次测试结束后，必须清理本次测试专门创建的一次性脚本、临时文件、临时目录、模拟配置、测试日志、生成数据及其他临时产物；清理要求见 19.3.1。

### 19.3.1 测试产物与临时文件清理（强制）

**测试必须做到创建可控、执行可复现、结束可清理。凡是仅为本次调试、验证或测试而临时创建的文件和资源，测试完成后必须删除，不得无故遗留在项目目录、系统临时目录或用户目录中。** 此要求同样适用于测试成功、测试失败、中断退出及提前终止等情况。

#### A. 必须清理的一次性测试产物

以下内容若仅为本次测试创建，测试结束后必须清理：

1. 一次性测试脚本、临时 Shell 代码、临时 Python/PowerShell 辅助脚本，以及临时生成的测试程序。
2. 临时输入文件、输出文件、模拟配置、虚拟证书、测试密钥、伪造数据、样例数据库和临时目录。
3. 测试日志、调试输出、命令结果快照、临时报告、覆盖率中间文件和性能分析文件。
4. 下载后仅用于本次测试的安装包、压缩包、二进制文件、依赖缓存及解压目录。
5. 测试创建的 PID 文件、Socket、锁文件、FIFO、临时端口占用、后台进程及临时服务。
6. 临时容器、测试专用网络、测试卷、测试镜像或其他由本次测试单独创建的外部资源。清理时只能按本次创建的准确名称或 ID 操作。
7. 测试过程中产生且不属于项目正式交付内容的构建产物、缓存和临时 Git 文件。

#### B. 必须保留的正式测试资产

**清理临时产物不等于删除测试代码。** 以下内容属于项目长期质量保障的一部分，除非用户明确要求删除，否则必须保留并纳入 Git 版本管理：

1. 正式测试套件，例如 `tests/` 下长期维护的 Bats 测试文件。
2. 为复现缺陷而新增的回归测试，以及已有测试的必要更新。
3. 测试所需且明确作为固定输入的 Fixture、Golden File、预期输出和最小化样例配置。
4. 测试运行说明、测试配置、Mock/Stub 实现，以及 CI 工作流中长期使用的测试辅助文件。

一次性创建、只用于本次手工验证的测试脚本必须删除；正式测试套件中的测试脚本必须保留。AI Agent 必须先判断文件用途，不能把正式回归测试误删为临时文件，也不能以“测试文件”为由保留本应清理的一次性脚本。

#### C. 创建临时文件的要求

1. 临时文件和目录应优先创建在操作系统提供的临时目录中，并使用 `mktemp` 生成不可预测且唯一的名称；不得使用固定文件名反复覆盖其他任务的文件。
2. 测试必须记录本次创建的临时路径和资源标识，只清理自己创建且能够明确确认归属的对象。
3. 优先将测试输入、输出和中间文件统一放入一个独立临时目录，便于集中清理。
4. 不得把临时文件随意写入项目根目录、用户主目录、系统配置目录或正式数据目录。确实需要在项目目录内验证时，应使用专用临时子目录，并确保测试结束后删除。
5. 不得通过修改 `.gitignore` 来代替实际清理；被忽略的临时文件仍然必须删除。
6. 不得复用或清空可能由用户、其他进程或其他任务创建的临时目录。

推荐在独立测试进程中使用 `mktemp` 和 `EXIT` Trap 管理临时目录。以下代码仅是嵌入独立测试入口的**临时资源管理片段，并非完整脚本**。若它被放入作为项目产品分发的独立可执行测试工具，该工具仍须遵守第 2 节的文件头、`SCRIPT_VERSION`、严格模式和适用的权限要求；Bats 测试文件及测试驱动本身不因被测程序要求 Root 而自动要求 Root，测试身份边界遵循 19.3 节。该片段会设置 `EXIT`、`HUP`、`INT`、`TERM` Trap，使用前必须确认这些 Trap 尚未承载其他必须保留的行为；如已有处理逻辑，必须合并到统一处理函数，不得只检查 `EXIT` 而覆盖信号 Trap。被 `source` 加载的库文件不得擅自安装或覆盖调用方的 Trap。

在 `mktemp -d` 的命令替换完成、路径写入 `TEST_TMP_DIR` 之前，仍存在极短的信号中断窗口；预先安装 Trap 可以缩小窗口，但不能证明该窗口内创建的目录一定能被当前 Shell 清理。因此，测试还应运行在可销毁的临时工作区或隔离环境中，并对无法确认归属的残留资源如实报告：

```bash
# 测试临时文件默认仅允许当前用户访问。
umask 077

# Root 测试进程不信任调用方 TMPDIR，固定使用系统临时目录；非 Root 可使用 TMPDIR。
# 后续会解析物理路径，因此允许 /tmp -> /private/tmp 等系统级符号链接。
if (( EUID == 0 )); then
    readonly TEST_TMP_ROOT='/tmp'
else
    readonly TEST_TMP_ROOT="${TMPDIR:-/tmp}"
fi
TEST_TMP_ROOT_REAL=""
TEST_TMP_DIR=""

cleanup_test_artifacts() {
    local exit_status=$?
    local temp_parent
    local temp_name

    trap - EXIT

    if [[ -n "$TEST_TMP_DIR" ]]; then
        temp_parent="${TEST_TMP_DIR%/*}"
        temp_name="${TEST_TMP_DIR##*/}"
        [[ -n "$temp_parent" ]] || temp_parent='/'

        if [[ "$temp_parent" == "$TEST_TMP_ROOT_REAL" && "$temp_name" == bash-test.* && -d "$TEST_TMP_DIR" && ! -L "$TEST_TMP_DIR" ]]; then
            if ! rm -rf -- "$TEST_TMP_DIR"; then
                printf '[ERROR] 无法清理测试目录：%s\n' "$TEST_TMP_DIR" >&2
                (( exit_status != 0 )) || exit_status=1
            fi
        else
            printf '[ERROR] 拒绝清理非预期路径或符号链接：%s\n' "$TEST_TMP_DIR" >&2
            (( exit_status != 0 )) || exit_status=1
        fi
    fi

    exit "$exit_status"
}

if [[ ! -d "$TEST_TMP_ROOT" ]]; then
    printf '[ERROR] 临时目录不存在或不可访问：%s\n' "$TEST_TMP_ROOT" >&2
    exit 1
fi

if ! TEST_TMP_ROOT_REAL="$(cd -- "$TEST_TMP_ROOT" && pwd -P)"; then
    printf '[ERROR] 无法解析临时目录的物理路径：%s\n' "$TEST_TMP_ROOT" >&2
    exit 1
fi

if [[ "$TEST_TMP_ROOT_REAL" == '/' ]]; then
    printf '[ERROR] 拒绝将文件系统根目录用作测试临时目录。\n' >&2
    exit 1
fi

if (( EUID == 0 )) && { [[ ! -k "$TEST_TMP_ROOT_REAL" ]] || [[ ! -O "$TEST_TMP_ROOT_REAL" ]]; }; then
    printf '[ERROR] Root 测试必须使用由 Root 拥有且带 sticky bit 的安全临时目录：%s\n' "$TEST_TMP_ROOT_REAL" >&2
    exit 1
fi

# 先安装 Trap，再创建目录，缩小创建成功后尚未注册清理 Trap 的时间窗口。
trap cleanup_test_artifacts EXIT
trap 'exit 129' HUP
trap 'exit 130' INT
trap 'exit 143' TERM

TEST_TMP_DIR="$(mktemp -d "${TEST_TMP_ROOT_REAL%/}/bash-test.XXXXXX")"

# 将本次测试产生的临时文件全部放在 "$TEST_TMP_DIR" 中。
# 测试结束、失败或收到终止信号时，由 EXIT Trap 统一清理。
```

#### D. 清理时机与安全边界

1. 正常测试完成后必须立即清理，不得等到下次构建、下次运行或用户提醒。
2. 测试失败或命令异常退出时，仍必须执行清理；不得因为测试失败就跳过清理。
3. 收到 `HUP`、`INT`、`TERM` 等可捕获信号时，应通过统一清理流程退出。对于 `KILL`、断电或 Runner 被强制销毁等无法捕获的情况，应使用 CI 临时工作区、容器或系统临时目录限制残留范围，并在后续运行中按明确的任务标识回收。
4. 删除前必须校验目标路径确实属于本次测试创建的临时路径；路径为空、为根目录、为用户主目录、为项目根目录或无法确认归属时，必须拒绝删除。
5. 禁止使用 `rm -rf "$TMPDIR"`、`rm -rf ./*`、无边界通配符或其他可能影响用户数据的清理命令。不得使用 `git clean -fdx` 清理测试环境，除非用户明确授权且已逐项确认删除范围。
6. 对测试启动的后台进程，只能终止本次测试启动并记录的 PID 或进程组；禁止使用宽泛的 `pkill`、`killall` 或按模糊名称批量终止进程。
7. 对测试创建的容器、网络、卷和服务，只能删除本次创建且通过名称、标签或资源 ID 确认的对象；禁止使用全局 prune 或清空共享资源。
8. 不得删除测试前已存在的文件、用户修改、正式配置、项目数据或其他任务的产物。执行前后应检查 Git 状态和相关目录差异，以区分原有内容与本次新增内容。
9. 清理动作本身失败时，必须报告残留资源的准确路径、名称或 ID，以及失败原因；不得宣称清理完成。若清理失败会影响安全、数据完整性或后续测试，应将任务标记为未完成。
10. 清理过程不得吞掉原始测试失败状态。测试失败后清理成功，最终结果仍为测试失败；测试本身通过但清理失败，也不得报告为完整通过。

#### E. Bats、CI 与 Git 要求

1. 使用 Bats Core 时，优先使用框架为每个测试提供的 `$BATS_TEST_TMPDIR` 存放临时文件；不得把临时产物写入仓库根目录。测试框架自动清理的范围应以当前版本文档为准，额外创建在该目录之外的资源仍须自行清理。
2. CI Runner 应优先使用临时工作区或隔离容器；Job 结束前应执行必要的清理步骤。不能仅依赖 Runner 最终销毁来掩盖本地测试脚本不具备清理能力的问题。
3. 在执行 `git add` 和创建 Commit 之前，必须清理本次产生的一次性测试产物，并检查 `git status --short`、`git diff --check` 和相关临时目录。
4. 正式测试文件、Fixture 和回归测试必须按项目要求纳入版本管理；一次性测试脚本、日志、临时配置和生成物不得进入 Commit。
5. 若用户明确要求保留测试报告、日志或复现材料，必须将其保存到用户指定的位置，并在交付说明中列出；不得将其误放进项目临时目录或未经许可提交到 Git。
6. 交付前必须报告临时测试产物是否清理、正式测试文件是否保留，以及是否存在未能清理的资源。

### 19.4 文档、配置和示例验证

- Markdown 文档修改后，必须检查标题结构、代码围栏、链接、拼写和示例一致性。
- 文档中的 Bash 示例应提取并运行 `bash -n`；构成完整脚本或影响项目脚本逻辑的示例，必须按 19.2 执行 ShellCheck。
- 配置文件修改后，必须使用对应程序的配置校验命令。
- CI、构建、格式化和静态分析均属于适用验证，不能只运行最简单的语法检查。

### 19.5 失败处理

- 发现测试失败时，必须定位原因、修复并重新运行受影响测试。
- 不得删除有效测试、跳过失败用例、关闭检查规则或降低断言标准来制造通过结果。
- 测试因依赖缺失、权限不足或环境限制无法执行时，必须明确标记“未执行”，说明原因和影响；不得写成“通过”。
- 仍有未解决失败时，不得宣称任务已完全验证通过。
- 所有适用检查通过后方可提交和交付；若用户要求紧急交付或外部条件导致无法通过，必须明确披露未通过项，不能伪造通过结果。

## 20. Git 版本管理与 AI Agent 工作流程（强制）

AI Agent 必须主动使用 Git 管理本项目代码、脚本、测试和文档。Git 是追踪、审查和回滚每次改动的依据。

### 20.1 自动检测与初始化 Git 仓库（强制）

**AI Agent 必须使用 Git 管理项目。若当前项目目录尚未处于 Git 仓库中，必须自动初始化，不得因为目录尚无 `.git` 而跳过版本管理，也不得默认要求用户手动执行 `git init`。**

开始修改前，必须先检查 Git 是否可用，以及当前目录是否已经位于某个仓库内：

```bash
command -v git >/dev/null 2>&1 || {
    printf '[ERROR] 未安装 Git，无法进行版本管理。\n' >&2
    exit 127
}

if repository_root="$(git rev-parse --show-toplevel 2>/dev/null)"; then
    printf '当前 Git 仓库：%s\n' "$repository_root"
else
    printf '[WARN] 当前目录暂未识别为 Git 工作树，必须先检查祖先目录中的 .git 标记和 Git 错误原因，再决定是否初始化。\n' >&2
fi
```

**重要：** `git rev-parse` 失败不一定代表“当前目录不是 Git 仓库”；也可能是仓库所有权安全检查（`dubious ownership`）、损坏的 `.git`、权限不足、环境变量覆盖或 Git 配置异常。不得把所有失败都直接当作无仓库并执行 `git init`。必须先检查当前目录及所有祖先目录中的 `.git` 目录或 gitfile，并识别错误原因；只在确认不存在可用或异常的上层仓库、且已确认当前目录就是项目根目录后，才能初始化。

执行规则：

1. 如果 `git rev-parse --show-toplevel` 成功，必须使用返回的仓库根目录；即使当前子目录没有自己的 `.git`，也不得在子目录中嵌套初始化另一个仓库。
2. 如果当前目录不属于任何 Git 仓库，必须自动在**当前任务对应的项目根目录**执行 `git init`。项目根目录优先依据用户指定的工作目录、项目清单文件（如 `package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`）和项目结构判断；不得把用户主目录、系统目录、临时目录或包含多个互不相关项目的公共父目录误判为项目根目录。
3. 如果任务明确针对某个文件或目录，且该目录就是独立项目目录，则在该项目目录初始化；不得擅自在其父目录或无关目录初始化。
4. 初始化前检查目标目录及 `.git` 路径。若存在损坏、无法识别或指向异常位置的 `.git` 文件/目录，不得删除、覆盖或重建；应先保留现场并报告问题。
5. `git init` 只创建仓库元数据，不得借初始化之名修改、清理、移动或删除项目现有文件。初始化完成后，必须再次执行 `git rev-parse --show-toplevel` 验证仓库根目录。
6. 初始化后必须在首次暂存、首次提交之前检查并创建或完善项目根目录的 `.gitignore`；具体规则遵循 20.1.1。已有 `.gitignore` 时只能审查并合并必要规则，不得直接覆盖用户已有内容。仓库状态检查按本节“仓库确认后的状态检查”执行。
7. `.gitignore` 完成后，必须检查未跟踪文件、已跟踪文件、被忽略文件和敏感信息。不得未经审查就执行 `git add .` 或 `git add -A`。首次建立基线时，只能暂存已确认属于项目、允许纳入版本控制且不含凭据、私钥、真实证书、个人数据、缓存、构建产物或大型无关文件的内容。
8. 如果首次基线涉及大量文件或无法确认文件归属，应只提交本次任务必需且已审查的文件；不得为了凑齐初始提交而把不明文件、秘密或用户无关数据纳入仓库。
9. 自动初始化仓库不等于自动创建远端。除非用户明确要求，不得擅自添加、修改或推送远程仓库。
10. 如果 Git 未安装、目录不可写、初始化失败或仓库状态异常，必须明确报告阻塞原因；不得谎称已启用 Git 管理。除用户明确要求之外，不得擅自安装 Git 或修改系统软件源。

#### 仓库确认后的状态检查

仓库识别或初始化完成后、开始修改前，必须检查：

```bash
git rev-parse --show-toplevel
git branch --show-current
git status --short --untracked-files=all
git log -5 --oneline
```

- 确认仓库根目录、当前分支、工作区状态和近期提交；尚无提交时，`git log` 的失败属于新仓库的正常状态，必须明确识别，不得伪造历史记录。
- 识别用户已有的未提交修改；不得覆盖、丢弃或擅自纳入无关内容。
- 若目标文件已有未提交改动，必须先区分用户原有内容与本次修改。
- 不得擅自切换分支、创建分支或更改远端设置；遵循项目已有策略。

### 20.1.1 `.gitignore` 创建、敏感文件排除与上传前审查（强制）

**每个由 AI 管理的项目仓库都必须在项目根目录维护 `.gitignore`。新仓库执行 `git init` 后，必须先创建 `.gitignore`，再进行任何首次暂存或提交；已有仓库如果缺少 `.gitignore`，也必须在本次提交项目文件前补建。** `.gitignore` 是防止本地配置、凭据和生成产物意外进入版本库的基础防线，不得省略。

#### 创建与维护规则

1. 必须先检查项目根目录是否已有 `.gitignore`。不存在时创建；存在时先阅读现有规则，再以增量方式合并，不得清空、覆盖或无理由重排用户规则。
2. `.gitignore` 必须放在实际 Git 仓库根目录；子项目确有独立忽略需求时，可以增加子目录 `.gitignore`，但不得用嵌套忽略文件代替根目录的基础安全规则。
3. 规则必须根据项目技术栈、部署方式和实际文件结构调整。不得只复制模板而不检查项目，也不得为了方便而忽略整个配置目录或所有配置文件。
4. 至少审查并按项目实际情况覆盖以下类别：
   - 环境变量与本地环境文件：`.env`、`.env.*`、本地环境覆盖文件；
   - 凭据和认证材料：Token、API Key、密码文件、账号凭据、云服务凭据、服务账号私钥；
   - 私钥与证书私密材料：`*.pem`、`*.key`、`*.p12`、`*.pfx`、`*.jks`、`*.keystore`，以及 SSH 私钥；
   - 含真实订阅地址、访问令牌、认证信息或个人数据的本地配置文件；
   - 运行日志、数据库、状态文件、PID、Socket、缓存、临时文件、备份文件；
   - 依赖目录、编译产物、测试输出、覆盖率报告和 IDE/操作系统生成文件。
5. 可参考以下基础规则，并根据项目实际目录补充；不得将示例视为无需审查即可照搬的完整规则：

```gitignore
# 缓存与生成产物。
```

6. 应根据实际项目为可安全提交的示例文件保留白名单，例如 `.env.example`、`.env.sample`、`config.example.yaml`、`config.example.json`。示例文件必须使用虚构值或明确的占位符，不得包含真实凭据、订阅链接、私钥或个人信息。
7. 不得无差别忽略 `*.yaml`、`*.yml`、`*.json`、`*.toml`、`*.conf`、`*.ini` 等全部配置格式；这些文件可能是项目必需的声明式配置、工作流、部署模板或测试 Fixture。应优先按具体文件名、目录或 `.local` / `.secret` 后缀精确排除。
8. 对 Mihomo、代理订阅、Docker、Kubernetes、云平台、数据库、部署工具等项目，必须特别检查配置文件是否包含订阅凭据、密码、Token、私钥、真实服务器地址或个人数据；必要时忽略真实运行配置，只提交脱敏模板和示例。
9. 修改 `.gitignore` 后，必须用 `git check-ignore -v <路径>` 验证敏感文件确实命中预期规则，并验证必须纳入版本控制的源代码、工作流、模板和示例文件没有被误忽略。
10. 必须检查 `git status --short --untracked-files=all`、`git status --ignored --short` 和 `git ls-files`，并在提交前审查暂存区文件清单及差异。不得仅凭 `.gitignore` 内容推断文件已受到保护。

#### 当前 Tools 项目的本地 AI 指令文件约定

1. 按用户明确要求，当前 Tools 项目仅忽略仓库根目录的 `AGENTS.md`，`.gitignore` 必须使用根目录限定规则 `/AGENTS.md`。该规则不应扩大为 `**/AGENTS.md`，也不自动忽略 `YAML_AGENTS.md` 或其他目录中的同名文件。
2. `AGENTS.md` 是本地 AI 开发指令文件，保留在当前工作目录供本地工具读取，但不纳入该仓库的 Git 版本控制。当前仓库根目录的 `.gitignore` 必须包含 `/AGENTS.md`，不得只依赖全局 Git 忽略配置。
3. 如果根目录 `AGENTS.md` 已被 Git 跟踪，仅增加忽略规则不会停止跟踪。用户明确要求忽略该文件时，必须使用 `git rm --cached -- AGENTS.md` 将其从索引移除，同时保留工作区中的实际文件；严禁使用 `rm` 删除本地文件。
4. 执行后必须验证：`git check-ignore -v AGENTS.md` 能命中根规则，`test -f AGENTS.md` 仍成功，且 `git ls-files --error-unmatch AGENTS.md` 不再成功。
5. 该文件被忽略意味着新克隆仓库不会自动获得这份本地规范。若未来需要让团队成员和 CI 共同遵循，应将需要共享的规则迁移到纳入版本控制的 `CONTRIBUTING.md`、项目文档、CI 检查或仓库规则中；不得通过忽略规则假设远端已经拥有本地文件。

#### 已跟踪文件与历史泄露处理

1. `.gitignore` 只影响尚未被 Git 跟踪的文件；对于已经提交或已进入索引的文件，新增忽略规则不会自动停止跟踪，也不会从 Git 历史中删除。
2. 如果发现敏感文件已经被跟踪，必须立即停止将其纳入新的提交，并向用户明确说明风险、文件路径和建议处置方式。不得擅自删除用户本地文件，也不得在未确认影响的情况下执行 `git rm --cached`、历史重写或强制推送。
3. 在获得授权后，可通过 `git rm --cached -- <path>` 停止跟踪并保留本地文件；随后还必须确认该文件已被 `.gitignore` 排除，并检查暂存区差异。
4. 如果凭据、Token、私钥或密码已经进入远程仓库或 Git 历史，仅从当前版本删除文件并不足以消除泄露风险。必须建议立即吊销或轮换凭据；清理历史、重写提交和强制推送必须经过用户明确授权，并评估对其他协作者的影响。
5. 任何情况下都不得把真实密钥复制到示例文件、测试日志、命令输出、Commit message 或交付说明中。

#### 首次提交与持续审查

- `.gitignore` 本身属于项目维护文件，必须纳入版本控制并与项目代码一起审查。
- 后续新增配置目录、部署方式、凭据文件、构建工具或测试工具时，必须同步评估是否需要更新 `.gitignore`。
- `.gitignore` 不能替代秘密扫描、权限控制、加密存储或凭据轮换；上传前仍必须审查暂存区内容。


### 20.2 AI 自动提交身份：GitHub Actions 默认 Bot（强制）

**AI Agent 创建的自动化 Git commit，作者（Author）和提交者（Committer）必须统一使用 GitHub Actions 默认 Bot 身份，不得使用 `ChatGPT JK789`、runner 系统用户、个人账号或其他未经指定的身份。** 该身份与脚本文件头中的 `author` 字段无关；脚本文件头继续遵守第 2 节规范。

固定身份如下（适用于 GitHub.com）：

```text
Name : github-actions[bot]
Email: 41898282+github-actions[bot]@users.noreply.github.com
```

#### 在 GitHub Actions 工作流中配置

在仓库检出完成后、创建 commit 之前，必须配置仓库级 Git 身份。下例中的 `actions/checkout` 固定 SHA 对应官方 `v7.0.1` 发布提交；升级时必须重新核实官方发布信息，不得长期机械复制示例版本。**以下仅展示完整工作流中的 `jobs` 片段，不是可独立运行的完整 Workflow 文件**；实际文件仍须按 GitHub Actions 要求定义顶层 `name`、`on` 等字段：

```yaml
jobs:
  update:
    runs-on: ubuntu-latest
    # 只有本 Job 需要推送 Commit 时才授予写权限；仅检查代码时应使用 contents: read。
    permissions:
      contents: write
    steps:
      - name: Checkout repository
        # actions/checkout v7.0.1；生产工作流固定到经过审查的完整 Commit SHA。
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1
        with:
          persist-credentials: true

      - name: Configure GitHub Actions bot identity
        run: |
          git config --local user.name "github-actions[bot]"
          git config --local user.email "41898282+github-actions[bot]@users.noreply.github.com"

      # 在测试通过、审查差异后，再执行 git add、git commit 和 git push。
```

要求：

1. 必须使用 `github-actions[bot]` 和上述完整 noreply 邮箱，大小写、方括号和邮箱格式不得随意改写。
2. GitHub Actions 示例必须固定到经过审查的完整 Commit SHA，避免只引用可移动的分支名或未经审查的浮动引用。上例对应官方 `actions/checkout v7.0.1` 发布提交；升级 Action 时必须核对官方 Release、完整 SHA、签名/来源及兼容性，不得仅凭网上复制的短 SHA 更新。
3. 必须使用仓库级配置（`git config --local`）；不得使用 `git config --global` 修改 Runner 或开发环境的全局身份。
4. 必须在第一次自动提交前配置，并通过 `git config --local --get user.name`、`git config --local --get user.email` 检查配置值。
5. 创建提交前，还必须用 `git var GIT_AUTHOR_IDENT` 和 `git var GIT_COMMITTER_IDENT` 检查实际生效的作者及提交者身份。若 `GIT_AUTHOR_*`、`GIT_COMMITTER_*` 环境变量或其他配置覆盖了 Bot 身份，必须先查明并安全处理；不得在身份不符时继续提交。
6. 在非 GitHub Actions 的临时执行环境中，若只需为单次 AI 自动提交指定该身份，优先对单次 `git commit` 使用 `git -c user.name=... -c user.email=...`，避免永久改变项目或用户的 Git 身份配置。
7. 不得修改用户个人的全局 Git 身份；不得把人工提交伪装成 Bot 提交。该规则只约束 AI Agent 创建的自动化提交。
8. Bot 身份仅决定 commit 中记录的作者和提交者信息，**不代表拥有仓库写权限，也不提供身份认证凭据**。
9. 若工作流需要推送，必须显式授予最小必要权限，例如工作流级或 Job 级 `permissions: contents: write`，并使用 `actions/checkout` 提供的有效凭据。仅运行检查或创建不推送的本地 Commit 时，应使用更小权限，例如 `contents: read`（若操作流程允许）。不得把 Token 写入脚本、命令参数、日志或仓库文件。
10. 若 `GITHUB_TOKEN` 权限不足、分支保护策略拒绝推送或事件来源限制写权限，必须报告真实原因；不得通过关闭保护规则、使用个人 Token 或扩大权限来擅自绕过。
11. 上述固定邮箱对应 GitHub.com 的 `github-actions[bot]`。若使用 GitHub Enterprise Server（GHES）或其他托管平台，必须先核实该实例支持的 Bot 身份，不得盲目套用 GitHub.com 的邮箱。
12. 处理来自 Fork 或其他不可信来源的 Pull Request 时，必须遵循最小权限原则：默认使用 `pull_request` 只读权限运行测试；不得在持有写权限 Token、部署密钥或其他秘密的 `pull_request_target` 工作流中检出并执行不可信 PR 的代码。确需自动写回时，必须将只读测试与受信任写操作拆分为独立 Job/Workflow，并验证触发来源、提交 SHA 和权限边界。
13. 不得把 `GITHUB_TOKEN`、PAT、部署密钥或其他 Secret 输出到日志、命令参数、工件或测试报告；第三方 Action 必须固定到经过审查的完整 SHA，且只授予完成任务所需的最小权限。

### 20.3 每项逻辑改动必须提交

1. **每完成一项逻辑完整的改动，都必须创建一个对应的 Git commit。** 不得把多个无关任务合并到一个提交，也不得长期积累未提交修改。
2. **本地忽略文件例外：** 当前 Tools 项目根目录 `AGENTS.md` 的忽略、保留和停止跟踪方式统一遵循 20.1.1“当前 Tools 项目的本地 AI 指令文件约定”。编辑该文件本身不要求 Git Commit；同一任务中的 `.gitignore` 和其他受跟踪文件仍必须按本节正常审查和提交。该例外不得扩大到其他代码、测试或文档。
3. 提交前必须完成相关测试和验证；适用测试未通过时不得把改动提交为已完成状态。
4. 提交前必须检查：

   ```bash
   git diff --check
   git diff
   git diff --cached
   git status --short
   ```

5. 优先使用明确文件路径暂存，例如 `git add path/to/script.sh path/to/test.bats`；禁止未检查就使用 `git add .` 或 `git add -A`。
6. 只提交本次任务的相关文件；不得混入用户已有修改、缓存、日志、临时文件、构建产物或秘密数据。
7. Commit 信息必须清楚说明变更目的，推荐 Conventional Commits：

   ```text
   feat(ssl): 增加证书自动续期检查
   fix(dns): 修复配置文件路径判断
   test(ssl): 增加非 root 权限回归测试
   refactor(common): 统一日志输出函数
   docs(agents): 完善 Bash 编码规范
   ```

8. 一个 commit 对应一个清晰、可追踪的逻辑改动；禁止使用“更新”“修改一下”“AI commit”等无意义信息。
9. 默认禁止 `git commit --amend`、强制推送和其他改写历史行为；只有用户明确授权时才可执行。
10. 未经用户明确授权，不得执行可能丢失工作成果的命令，例如 `git reset --hard`、`git clean -fd`、`git checkout -- <文件>`、`git restore <文件>`。
11. 需要撤销已提交改动时，优先使用可审查的 `git revert`，并先确认目标提交及影响范围。
12. 未能使用规定的 GitHub Actions Bot 身份、仓库只读、Hook 失败或提交被策略拒绝时，不得伪造提交、绕过保护措施、改用个人身份或擅自修改全局配置；必须报告原因。
13. 用户明确要求不提交或项目规则禁止提交时，遵循该明确要求，并在交付说明中注明未提交原因。

### 20.4 提交后检查

每次提交后必须执行并确认：

```bash
git status --short
git log -1 --oneline
```

- 确认 commit 确实创建成功。
- 确认提交内容只包含本次改动。
- 确认工作区没有遗留本次任务的意外修改。
- 不得把 commit 哈希或状态凭空写入交付说明。

### 20.5 AI Agent 标准工作顺序

AI Agent 必须按以下阶段执行；各阶段的具体命令和限制以引用章节为准：

1. **理解项目：** 阅读本规范、相关代码、测试和项目说明，明确需求、影响范围和最小修改方案。
2. **保护工作区：** 按 20.1 检查或初始化 Git 仓库，审查用户已有修改，并按 20.1.1 完成 `.gitignore` 与敏感文件检查。
3. **实施修改：** 按本规范编写代码，并同步维护必要的注释、帮助信息、配置说明和文档。
4. **判断版本：** 按 20.6 判断是否需要升级及升级级别；此阶段只作判断，不提前改写版本记录。
5. **验证与清理：** 更新测试，执行语法、ShellCheck、行为和配置验证；修复问题后重跑，并按 19.3.1 清理一次性测试产物。
6. **审查与提交：** 测试通过后、最终提交前，按 20.6 同步确有必要的版本信息和变更记录，再完成差异与暂存区审查；确认没有秘密或无关文件，按 20.2 配置并核验 Bot 身份，再依 20.3 创建对应 Commit。
7. **提交后核验：** 按 20.4 检查 Commit、身份和工作区状态。
8. **交付：** 按第 23 节报告变更、Commit、真实验证结果和未解决限制。

### 20.6 版本号管理与升级规则（强制）

版本号用于表达软件或脚本的功能变化和兼容性，不是提交次数、修改次数或日期编号。AI Agent 必须先分析变更影响，再决定是否升级以及升级哪个字段；不得凭感觉递增、随意跳号、降级或伪造版本。

#### 20.6.1 统一版本格式

1. 稳定版本统一采用语义化版本（Semantic Versioning，SemVer）格式：`MAJOR.MINOR.PATCH`，即 `主版本.次版本.修订版本`，例如 `0.2.3`、`1.4.0`。
2. 三个部分必须是非负整数，不得省略部分、添加前导零（数字 `0` 本身除外），不得使用日期、构建次数或 Git 短哈希代替版本号。
3. 稳定版本号不得添加 `v` 前缀。脚本头部 `ver`、版本常量和版本文件使用 `1.2.3`；Git 标签可按项目惯例使用 `v1.2.3`。
4. 预发布版本可使用 SemVer 后缀，例如 `1.2.0-alpha.1`、`1.2.0-beta.2`、`1.2.0-rc.1`。只有项目明确采用预发布流程时才使用，不得把预发布版伪装成稳定版。
5. 构建元数据可按需使用 `1.2.3+build.45`，但构建元数据不得用于表达兼容性，也不得替代主、次、修订版本升级。
6. **当前 Tools 项目的默认发布策略为稳定版三段式 `X.Y.Z`。** 所有脚本的 `ver` 和 `SCRIPT_VERSION` 默认只允许该格式；不得仅因 SemVer 标准允许预发布或构建元数据，就自行把它们引入项目。
7. 只有用户或项目明确启用预发布/构建版本通道后，才允许使用 `-alpha`、`-beta`、`-rc` 或 `+build` 等后缀。启用前必须同步扩展版本校验、静态提取、SemVer 比较、菜单显示和测试；在这些能力完成前必须拒绝此类版本，不得部分支持。
8. 除非项目已有并明确记录其他版本方案，否则必须遵守本节规则。不得混用日期版本、四段版本和 SemVer。

#### 20.6.2 主版本、次版本和修订版本的升级条件

必须依据对用户可见行为、公开接口和兼容性的实际影响决定升级级别：

| 升级类型 | 版本变化 | 适用情况 | 示例 |
| --- | --- | --- | --- |
| 修订版本（PATCH） | `1.2.3` → `1.2.4` | 修复缺陷、安全修复且不破坏兼容性、纠正错误判断、修复异常退出或边界问题；不增加破坏性接口 | 修复证书到期时间计算错误 |
| 次版本（MINOR） | `1.2.3` → `1.3.0` | 向后兼容地增加功能、命令行选项、可选参数、配置项或公开能力；弃用旧功能但暂时保持兼容 | 新增 `--dry-run` 参数且不改变旧参数行为 |
| 主版本（MAJOR） | `1.2.3` → `2.0.0` | 引入不兼容变更，包括删除或重命名公开参数、函数、配置键、文件格式，改变参数含义、默认行为、输出契约或最低运行环境，导致现有用户需要修改调用方式或配置 | 删除旧配置项并要求用户迁移到新格式 |

补充判定要求：

1. 是否升级必须以兼容性和行为影响为依据，不以修改了多少行代码、文件数量或开发耗时为依据。
2. 同时包含多个类型的改动时，按其中影响最大的类型升级。例如一次提交既修复缺陷又增加兼容功能，至少按次版本升级；包含不兼容变更时按主版本升级。
3. 纯注释、拼写、格式、文档、测试用例或 CI 内部维护改动，若不改变交付程序的行为和用户接口，默认不升级程序版本。若项目发布流程明确将这些改动作为独立发行内容，则遵循项目已记录的发布策略。
4. 纯内部重构若经测试确认外部行为和接口完全不变，默认不升级版本；若重构改变性能、安全性或运行要求并影响用户，应根据实际影响选择修订或主版本。
5. 依赖项升级不等于程序版本自动升级。必须评估依赖升级是否修复缺陷、增加功能、改变兼容性或影响运行行为，再按本表决定。
6. 仅更新 `date`、作者信息或文件头排版，不构成版本升级理由。
7. 不能确定兼容性影响时，不得擅自选择较低版本掩盖风险；必须检查调用方、配置、文档和测试，并在交付说明中披露仍无法确认的部分。

#### 20.6.3 `0.x.y` 开发阶段规则

1. `0.y.z` 表示尚未宣告稳定的初始开发阶段，公开接口和行为可能发生变化；不得向用户承诺其具备 `1.x` 的稳定兼容性。
2. 在 `0.x` 阶段，普通兼容性缺陷修复递增修订号，例如 `0.2.3` → `0.2.4`；向后兼容的新功能可递增次版本，例如 `0.2.3` → `0.3.0`。
3. 在 `0.x` 阶段发生不兼容的公开接口或配置变更时，也递增次版本并将修订号归零，例如 `0.2.3` → `0.3.0`。不得在尚未达到 `1.0.0` 时擅自将其解释为 `1.0.0`。
4. 只有项目负责人或用户明确决定进入稳定发布阶段，并完成必要兼容性、测试和文档审查后，才可从 `0.x` 升级到 `1.0.0`。
5. 新建且没有任何既有版本记录的开发中脚本，默认从 `0.1.0` 开始；若用户明确要求首个稳定正式版本，可从 `1.0.0` 开始。已有脚本必须沿用其真实版本，不得因 AI 接手而重置。

#### 20.6.4 脚本头部、运行时和项目版本源

1. 对独立 Bash 脚本，若项目没有独立版本文件或发布清单，文件头部 `ver` 是该脚本的版本记录来源；脚本提供 `--version` 时，输出必须与 `ver` 一致。
2. 对有统一发布版本的项目，必须先识别项目指定的唯一版本源，例如 `VERSION`、项目清单或项目元数据。脚本头部、运行时 `--version`、README、变更日志和发布标签均为同步信息，不得各自维护互相冲突的版本。
3. 不得因为一个项目中的某个脚本发生变化，就无条件升级所有脚本的 `ver`。只升级实际发生行为或接口变化、且由独立版本管理的组件；若项目采用统一整体版本，则按项目级变更影响升级统一版本。
4. 同一组件不得同时存在多个互相矛盾的“当前版本”。如果发现头部、版本文件、命令输出或 Git 标签不一致，必须先确认项目约定的权威来源，再修复同步信息；不得自行猜测哪个版本正确。
5. `--version` 输出、版本常量、文件头 `ver` 及项目版本文件必须使用同一版本值。若版本值在多个位置重复保存，必须通过测试或 CI 检查其一致性。
6. 独立、可执行 Bash 脚本的 `SCRIPT_VERSION` 声明格式、唯一性、权威来源和与文件头 `ver` 的一致性，统一遵循第 20.6.14 节；本项不重复定义常量语法。项目若另有 `VERSION` 文件或发布清单，必须明确它与脚本版本常量的权威关系，并通过测试/CI 验证一致，不得在运行时执行不可信文件来动态生成版本。
7. 配置格式版本、数据库迁移版本、API 版本、协议版本和程序发布版本属于不同概念，必须分别命名和管理；不得用程序版本号代替数据迁移编号，也不得因程序升级就无理由修改配置 Schema 版本。

#### 20.6.5 版本升级触发条件与禁止情形

1. 修改脚本功能、公开参数、配置行为或用户可见输出时，必须按 20.6.2 和 20.6.3 判断升级级别，并在本次逻辑改动中同步必要的版本信息。
2. 纯文档、纯注释、纯格式或仅新增测试，且不改变交付程序行为和接口时，默认不升级程序版本；具体判定遵循 20.6.2。
3. 同一逻辑改动只在最终准备提交时确定并更新一次版本，不得因开发过程中的多轮修复重复递增。
4. 版本不得降低、回退到已发布过的旧值或复用已发行版本号；撤销已发布功能时，应发布新的合法版本。
5. 不得擅自将项目从 `0.x` 升到 `1.0.0`，不得擅自执行大版本发布，也不得将未完成、未验证的变更标记为正式稳定版本；`0.x` 阶段的处理遵循 20.6.3。

#### 20.6.6 变更日志与升级说明

1. 若项目已有 `CHANGELOG.md`、Release Notes 或同等变更记录，所有正式版本升级必须同步更新，不得只改版本号而遗漏用户可见的变化说明。
2. 若项目没有变更日志，单文件脚本的普通补丁可在 Commit 说明中记录；当项目需要对外发布、存在多个用户可见功能或需要迁移说明时，应创建并维护 `CHANGELOG.md`，不得无故重复创建不同名称的变更日志。
3. 变更日志应按版本和日期组织，优先区分 `Added`、`Changed`、`Deprecated`、`Removed`、`Fixed`、`Security` 等类别；内容说明用户可感知的变化，不得简单复制 Commit 列表。
4. 存在不兼容变更时，必须说明受影响范围、迁移步骤、旧行为终止方式和必要的备份/回滚方法。
5. 不得把未实现、未测试或计划中的功能写成已发布功能；日期必须真实，不得提前填写未来发布日期。

#### 20.6.7 Git Commit、Tag 与版本对应关系

1. 版本号升级必须与对应代码变更一起纳入同一个逻辑 Commit，确保检出该 Commit 后，代码与版本信息一致。
2. Commit 仍须遵循 20.3 的一项逻辑改动一个 Commit 原则。版本升级不是将无关修改打包提交的理由。
3. 常规开发 Commit 不要求每次都创建 Git Tag；只有项目明确进入发布节点时，才创建与版本号对应的 Tag。
4. 稳定版本 Tag 默认使用 `vMAJOR.MINOR.PATCH`，例如 `v1.2.3`；预发布 Tag 使用完整预发布标识，例如 `v1.3.0-rc.1`。若项目已有标签格式，必须沿用，不得混用。
5. 创建发布 Tag 前必须确认版本号唯一、工作区干净、目标 Commit 正确，且相关测试、静态检查、配置校验和发布准备全部通过。
6. 发布 Tag 应使用有说明的附注标签（annotated tag），并写明版本和主要变更。不得覆盖、移动或强制重写已经发布的 Tag。
7. 未经用户或项目发布流程明确授权，不得推送 Tag、发布 Release、部署生产环境或向远程仓库发布制品。创建本地 Tag 也必须符合项目既定发布授权约定。
8. 若版本号已被远程仓库或正式发布占用，不得复用；应根据变更影响选择下一个合法版本，并说明原因。

#### 20.6.8 版本升级后的验证要求

版本升级本身也是代码变更，必须验证版本记录准确且可复现：

1. 检查版本字符串符合项目约定的 SemVer 格式；稳定版本必须为 `X.Y.Z`，预发布版本必须具有明确的预发布标识。
2. 若脚本支持 `--version`，必须实际执行并确认输出与文件头 `ver` 或项目权威版本源一致。
3. 若存在多个版本记录位置，必须运行一致性测试，确保脚本头部、版本常量、项目清单、文档和发布元数据没有漂移。
4. 版本升级不得破坏 `--help`、参数解析、安装脚本、更新脚本、升级检测和回滚逻辑；相关路径必须纳入测试。
5. 主版本升级必须增加或更新不兼容变更测试与迁移说明；次版本升级必须测试新增功能及旧用法兼容性；修订版本升级必须测试对应缺陷的回归用例。
6. 必须重新运行适用的 `bash -n`、ShellCheck、Bats 和项目其他验证；不得因改动只有一行版本号而跳过针对版本输出或版本同步的测试。
7. 验证失败时不得创建发布 Tag 或宣称版本升级完成；必须修复并重跑所有受影响的检查。

#### 20.6.9 AI Agent 版本升级执行流程

本节只规定版本处理的执行顺序；升级条件、版本来源和验证标准分别以 20.6.2、20.6.3、20.6.5、20.6.8 为准，不在此重复定义：

1. 修改前检查文件头 `ver`、项目版本文件、`--version` 输出、CHANGELOG、Git Tag 和历史 Commit，确定真实版本及权威来源。
2. 根据 20.6.2、20.6.3 和 20.6.5 判断是否升级及升级级别；同时检查用户已有修改和历史版本不一致，不得擅自覆盖无关内容。
3. 完成代码和相关测试后，在最终准备提交时一次性同步必要的版本信息、变更日志和迁移说明。
4. 按 20.6.8 完成版本验证，再按 20.2 至 20.4 执行提交身份核验、Commit 和提交后检查。
5. 只有获得用户或项目发布流程授权时，才创建 Tag 或 Release。
6. 交付时报告旧版本、新版本、升级级别、判断依据、权威版本来源、实际验证结果和对应 Commit；未升级时说明判断依据。

#### 20.6.10 远程版本来源与版本发现（强制）

升级管理脚本必须能够在执行更新前，可靠地取得目标项目当前可用的正式版本。**禁止把“最新版本号”硬编码在升级脚本中，也禁止仅凭下载文件名、页面标题、README 文本或未经校验的字符串推断版本。**

1. 每个项目必须明确唯一、可信的版本权威来源（Version Source），并记录来源类型、仓库地址、版本字段、稳定版/预发布版策略及回退策略。优先使用项目正式发布渠道；不得混合多个来源后随意选择较大的版本。
2. 若项目以 GitHub Releases 发布，优先使用 GitHub 官方 REST API 获取发布元数据，并从响应的 `tag_name` 字段读取版本标签；不得通过抓取 GitHub HTML 页面来解析版本。
3. GitHub `GET /repos/{owner}/{repo}/releases/latest` 返回最新发布的正式 Release，即非 Draft、非 Prerelease 的发布项，排序依据为 `created_at`。**该接口不等同于“SemVer 数值最大的版本”**。只有当项目保证正式发布顺序与版本顺序一致时，才可直接将其作为最新稳定版本来源。
4. 若项目要求选择 SemVer 数值最高的版本，必须分页获取符合条件的 Release 或 Git Tag，过滤掉 Draft、Prerelease（除非明确启用预发布通道）和不符合项目版本规则的标签，再按 SemVer 规则比较；不得只取 API 第一条便假定它一定是数值最大版本。
5. 若项目使用 Git Tag 而不是 GitHub Release，必须使用 GitHub 官方 Tags API 或项目明确的 Git 服务 API。普通 Tag 不一定对应可下载、可安装的正式发行包；确认存在对应制品及校验信息后，才允许进入安装阶段。
6. 若项目以 `VERSION` 文件、发布清单、软件包仓库或自建更新 API 为权威来源，必须按项目指定格式读取，并验证返回值与目标项目、发行通道和制品相匹配。不得擅自改用另一个来源覆盖权威来源。
7. 稳定通道默认排除 Alpha、Beta、RC、Draft 和其他预发布版本。只有用户或项目配置明确启用预发布通道时，才允许检查并安装预发布版本；必须在界面和日志中清楚标注版本通道。
8. 版本标签只允许执行项目明确约定的标准化处理，例如移除一个位于开头的 `v`；不得随意删除前缀、后缀或非数字字符来“修复”无法识别的标签。
9. 获取到版本后，必须验证它符合项目声明的 SemVer 格式和允许的通道。缺失字段、空值、JSON 格式错误、意外 HTML、异常前缀、非预期仓库或不合法版本，均视为版本发现失败。
10. 必须在本次运行的终端结果中说明查询使用的权威来源、仓库/项目标识、通道、远程版本和查询结果；不得把缓存值或上一次运行结果冒充本次在线查询结果。不得为此创建持久化日志文件。

#### 20.6.11 升级管理脚本的强制行为（强制）

凡是负责检查更新、下载新版本、替换程序或自我更新的脚本，必须遵循以下完整流程；不得只下载一个地址后直接覆盖现有程序：

1. **读取本地版本：** 对自更新管理脚本，优先读取脚本内嵌的 `SCRIPT_VERSION`；其他程序读取项目规定的权威本地版本源。若脚本头部 `ver`、`SCRIPT_VERSION`、`VERSION`、运行时 `--version` 等记录不一致，必须停止自动更新并报告冲突，不得猜测一个版本继续执行。
2. **获取远程版本：** 通过 20.6.10 指定的可信来源获取远程版本，并严格校验格式、仓库身份和发布通道。获取失败、超时、限流、认证失败或响应不可解析时，必须安全失败；不得把空字符串、`null`、HTTP 错误页或缓存版本当作新版本。
3. **正确比较版本：** 按 SemVer 规则比较本地与远程版本，必须分别比较 MAJOR、MINOR、PATCH 和预发布标识。禁止使用普通字符串字典序比较（例如 `[[ "$remote_version" > "$current_version" ]]`）。若项目只允许稳定版，可明确拒绝预发布版本；若支持预发布，必须实现并测试完整 SemVer 优先级规则。
4. **判断更新状态：** 远程版本高于本地版本才可进入更新流程；相同版本应提示已是最新版本并退出成功；远程版本低于本地版本时必须阻止降级，除非用户明确指定并授权回滚流程。不得将版本相同误判为更新，也不得将 `1.10.0` 错判为低于 `1.9.0`。
5. **锁定目标发行版本：** 版本确认后，后续下载必须绑定到同一个不可变 Tag、Release ID 或制品版本。不得先查询“最新版本”，再下载一个可能已变化的 `latest` 浮动地址，造成版本元数据与实际制品不一致。
6. **校验下载来源与制品：** 下载地址必须来自预先配置或可信发布元数据，并校验 HTTPS、预期主机、仓库、制品名称、目标平台和架构。下载的文件必须使用发布方提供的 SHA-256 校验值、签名或等价可信机制验证；仅对下载文件自行计算哈希、却没有可信期望值，不构成完整性验证。
7. **先验证再替换：** 必须先下载到安全临时目录，验证摘要/签名、文件类型、版本信息、权限和必要的语法/完整性测试。不得使用 `curl ... | bash`、`wget ... -O- | sh` 或同类管道直接执行未经验证的远程内容。候选脚本的静态版本识别及自更新专用安全验证，统一遵循第 20.6.16 节。
8. **安全更新：** 在备份现有文件后，使用同一文件系统内的临时文件执行原子替换；保留项目要求的所有者、权限和必要属性。替换失败时应恢复备份；不得留下半写入文件或破坏现有可用版本。
9. **自我更新：** 自更新后的隔离测试、版本核验和专用回归测试统一遵循第 20.6.17 节。当前进程不得假定替换后的代码会在本次运行中自动生效，应提示用户在下一次正常启动时使用新版本。
10. **交互与自动化：** 交互模式应在破坏性替换前清楚展示当前版本、目标版本、来源和影响，并按项目约定要求确认；非交互模式只能在明确启用自动更新且具备授权时执行，不得因没有 TTY 而默认同意。
11. **幂等与并发控制：** 更新脚本必须防止多个实例同时更新同一目标；本机支持时优先使用进程持有型锁（例如 `flock`），使进程退出后自动释放。若使用 PID 锁文件，必须验证 PID、进程身份/启动时间和主机标识，不能仅凭锁文件年龄判断陈旧，也不得误杀 PID 已被复用的其他进程。重复运行不得重复下载、重复覆盖或破坏配置。
12. **回滚：** 必须明确备份位置、回滚触发条件和回滚验证方法。回滚是明确的受控操作，不得以降低版本号伪装成普通升级；所有回滚操作必须记录旧版本、新版本、原因和结果。
13. **Root 与路径安全：** 更新脚本必须遵守本规范的 Root 检查要求；所有安装路径必须规范化并限制在预期目录，禁止对空路径、根目录或未经验证的用户输入执行覆盖、删除和递归操作。默认拒绝把符号链接作为待替换目标；若项目安装路径确实使用符号链接，必须先解析真实目标、验证其位于允许目录并明确替换的是链接还是目标文件，禁止跟随用户可控链接覆盖任意文件。临时下载文件应限制权限，替换用临时文件必须创建在目标文件同一文件系统/目录中，以确保原子替换条件成立。
14. **结果报告：** 更新结束必须向终端报告本地旧版本、远程目标版本、最终安装版本、制品来源、完整性校验结果、更新/跳过/失败状态及回滚结果。不得只输出“更新成功”而不验证安装后的版本；不得为结果报告创建持久化日志文件。
15. **更新器与发布 CI 分工：** ShellCheck、完整自动化测试和发布验收由发布方 CI 执行；目标主机更新器不应依赖 ShellCheck 才能运行，但必须验证来源、签名/摘要、版本、平台/架构和 Bash 语法。静态分析门禁遵循第 19.2 节。

#### 20.6.12 GitHub Releases 版本发现函数参考实现

项目使用 GitHub Releases 且标签格式为稳定版 `X.Y.Z` 或 `vX.Y.Z` 时，可采用以下函数作为基础实现。`OWNER/REPO` 必须来自项目配置，不得使用用户未经验证的输入拼接任意 URL；该函数只负责获取并校验版本，不负责下载、安装或替换程序。

```bash
# 获取 GitHub 仓库最新正式 Release 的 SemVer 版本。
# 参数：$1 表示 GitHub 仓库标识，格式为 OWNER/REPO。
# 输出：标准化后的 X.Y.Z 版本号，仅写入标准输出。
# 返回：成功时返回 0；依赖缺失、网络失败或版本无效时返回非 0。
get_latest_github_release_version() {
    local repository="${1:-}"
    local response
    local tag_name
    local version
    local api_url

    if [[ ! "$repository" =~ ^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$ ]]; then
        printf '[ERROR] GitHub 仓库标识格式无效：%s\n' "$repository" >&2
        return 2
    fi

    if ! command -v curl >/dev/null 2>&1; then
        printf '[ERROR] 缺少必要依赖：curl\n' >&2
        return 127
    fi

    if ! command -v jq >/dev/null 2>&1; then
        printf '[ERROR] 缺少必要依赖：jq\n' >&2
        return 127
    fi

    api_url="https://api.github.com/repos/${repository}/releases/latest"

    if ! response="$(curl \
        --fail \
        --silent \
        --show-error \
        --proto '=https' \
        --tlsv1.2 \
        --connect-timeout 10 \
        --max-time 30 \
        --max-filesize 1048576 \
        --retry 3 \
        --retry-delay 1 \
        --header 'Accept: application/vnd.github+json' \
        --header 'X-GitHub-Api-Version: 2026-03-10' \
        "$api_url")"; then
        printf '[ERROR] 获取 GitHub 最新 Release 失败。\n' >&2
        return 1
    fi

    if ! tag_name="$(jq -er '.tag_name | strings | select(length > 0)' <<< "$response")"; then
        printf '[ERROR] Release 响应缺少有效的 tag_name。\n' >&2
        return 1
    fi

    # 仅移除开头的单个 v，不对其他标签格式进行猜测式修正。
    version="${tag_name#v}"

    if [[ ! "$version" =~ ^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$ ]]; then
        printf '[ERROR] Release 标签不是受支持的稳定 SemVer：%s\n' "$tag_name" >&2
        return 1
    fi

    printf '%s\n' "$version"
}
```

使用要求：

1. 该函数依赖 `curl` 和 `jq`，必须先检查依赖；不得把依赖缺失当作“没有更新”。
2. 该接口只返回 GitHub 定义的最新正式 Release（非 Draft、非 Prerelease），并按 Release 的 `created_at` 排序；若项目要求数值最大的 SemVer，必须改用分页列表并执行 SemVer 比较，不能直接复用此函数结果作为最高版本。示例将元数据响应体限制为 1 MiB，防止异常响应无限占用内存；修改限制时必须结合 API 响应结构评估，不得完全移除响应大小约束。
3. 该示例只接受稳定的三段式 `X.Y.Z` 标签。若项目采用 `release-1.2.3`、四段版本或预发布版本，必须按项目明确约定扩展解析规则，并增加相应测试；不得简单放宽正则以接受任意字符串。
4. 该示例不自动跟随 API 重定向，以免把固定 API 请求转发到未经校验的主机。若仓库迁移导致 API 返回重定向，应先审查目标仓库和最终主机，再更新受信任的仓库配置；不得为了消除 301/302 直接加入无主机限制的 `--location`。
5. GitHub API 版本 Header 应在项目中统一管理；升级 API 版本时必须验证响应字段及兼容性，不得依赖未验证的字段。示例中的 `2026-03-10` 是 GitHub 已发布的 REST API 版本；未来维护者仍须在修改时核实该版本是否受支持及是否引入破坏性变更，不得把示例日期视为永久固定值。
6. 如果项目使用私有仓库，Token 必须通过安全环境变量或受保护的凭据机制提供；不得写入脚本、命令行日志或 Git。公共仓库读取不得无故要求用户提供 Token。
7. 调用函数后必须再次验证返回值，并通过经测试的 SemVer 比较函数判断是否需要升级；此函数本身不代表已完成版本比较或更新。

#### 20.6.13 版本发现与升级测试要求（强制）

升级管理脚本必须具备可重复运行的自动化测试。测试不得依赖真实生产更新、真实系统覆盖或未经授权的远程写操作。

至少覆盖以下场景：

1. 返回合法 `1.2.3` 和 `v1.2.3` 标签时，能够取得标准化版本。
2. 版本比较正确处理 `1.10.0` 大于 `1.9.0`、`2.0.0` 大于 `1.99.99`，不得按字符串字典序比较。
3. 本地与远程版本相同，正确判断为无需更新。
4. 远程版本低于本地版本，默认拒绝降级。
5. 稳定通道正确排除 Alpha、Beta、RC、Draft；预发布通道只有显式启用后才接受预发布版本。
6. 缺少 `tag_name`、空字段、非法 SemVer、意外前缀、重复 `v`、JSON 损坏或 HTML 错误页时，必须失败且不得修改现有文件。
7. DNS、连接超时、TLS 验证、HTTP 404、403、429、5xx、API 限流和网络中断时，必须报告失败，不得把失败响应解析为版本号。
8. 下载文件与目标版本不一致、摘要不匹配、签名无效、平台/架构错误或制品来源不可信时，必须拒绝安装。
9. 替换中断、磁盘空间不足、权限不足或回滚失败时，必须保留并报告可恢复状态，不得谎报更新成功。
10. 两个升级进程并发执行时，只能有一个实例获得更新锁；另一个必须安全退出或等待。
11. 管理脚本自身的自更新测试不在本节重复定义，统一遵循第 20.6.17 节。
12. `--check` / `--dry-run` 等检查模式不得修改系统、正式脚本、配置文件或安装目录。

测试时应使用 Mock HTTP 响应、固定 JSON Fixture、临时安装目录和可控校验数据；测试完成后按 19.3.1 清理所有一次性测试脚本、临时文件、下载文件、日志和目录，正式回归测试及 Fixture 必须保留。

**更新脚本最终原则：先确定权威来源，再取得并验证版本；先比较版本，再下载固定制品；先验证完整性，再原子替换；最后核验运行版本和回滚能力。任何一步无法确认，都必须停止更新并保留当前可用版本。**

#### 20.6.14 所有独立 Bash 脚本必须声明 SCRIPT_VERSION（强制）

所有独立、可执行的 Bash 脚本，不论属于终端管理、一次性安装、部署初始化、直接执行工具或简单选择脚本，都必须在全局常量区域声明唯一的 `readonly SCRIPT_VERSION`。该常量只用于准确标识脚本自身版本，**不代表脚本必须支持在线检查、下载、替换或自动升级**。当前 Tools 项目统一使用稳定版三段式 `X.Y.Z`；在预发布/构建版本的解析、比较、提取和测试能力未完整实现前，不得使用 `-alpha`、`-beta`、`-rc` 或 `+build` 后缀。

具体声明格式、一致性、权威版本来源和更新同步要求统一见 20.6.14.2；脚本类型与自更新适用范围统一见 20.6.14.1。其他章节不得重复定义另一套 `SCRIPT_VERSION` 声明方式。

#### 20.6.14.1 脚本类型判定与自更新适用范围（强制）

AI Agent 在设计版本展示、更新入口和自更新功能之前，必须先判断脚本的实际用途与运行方式。版本标识是所有独立可执行脚本的统一要求；远程自更新机制只在适用场景中启用。

**当前 Tools 仓库的自更新实现范围：** 目前唯一明确具备管理脚本自更新功能的是 `Script/mihomo/mihomo.sh`。其他 Bash 脚本即使声明 `SCRIPT_VERSION`，也只表示记录和识别自身版本；不得据此推断它们需要联网检查、下载、替换或回滚功能。除非用户明确提出，或后续项目需求、发布渠道和安全替换条件经过评估并形成明确约定，否则不得擅自给其他脚本增加自更新功能。若未来新增自更新脚本，必须先更新本节的项目实施范围，并完整满足 20.6.10 至 20.6.17 的要求。

1. **终端管理型脚本：** 长期安装或放置在固定路径、供用户反复调用，并负责管理软件、服务、配置、运行状态或生命周期的脚本，属于终端管理型脚本。只有在存在稳定可信的发布渠道、安全可替换的安装路径，且项目或用户确实需要自更新时，才实现独立的“更新管理脚本”能力。管理操作统一通过现有交互式主菜单提供，不得另设 CLI 子命令，也不得为了自更新增加命令行子命令。若同时管理 Mihomo 等软件，必须把“更新被管理软件”和“更新脚本自身”拆分为不同菜单项、函数和提示。
2. **一次性安装、部署或初始化脚本：** 运行一次即完成任务。必须遵循通用版本声明要求；除非用户明确要求或脚本实际作为长期管理工具分发，否则不得增加在线检查、更新菜单、自动下载、自我覆盖或回滚框架。
3. **直接执行型工具脚本：** 通过命令行完成一项明确任务后退出。不得仅为了版本标识而增加网络请求、更新检查、下载器或自更新逻辑。
4. **简单选择或短流程脚本：** 只提供少量选项、完成单一选择或执行短流程。不得将其扩展为完整管理菜单，也不得强制增加“更新脚本”菜单项或后台更新机制。
5. **库文件和被 `source` 加载的模块：** 不得添加交互菜单、自更新入口或加载时联网行为。只有模块本身作为独立发布组件进行版本管理时，才按项目约定记录模块版本；不得把调用方脚本版本误作模块版本。
6. **判定依据：** 是否需要自更新，应综合脚本是否长期驻留、是否有明确可信的远程发行来源、是否有安全可替换的安装路径，以及用户/项目是否确实需要该能力。函数名中出现 `update`、脚本包含少量菜单选项或脚本可以联网，都不足以单独证明需要自更新。
7. **不得过度设计：** 不适用自更新的脚本只需维护自身版本标识。不得为追求形式统一而复制大型管理脚本的菜单、Release API 查询、SemVer 比较、下载校验、原子替换和回滚代码。
8. 20.6.15 至 20.6.17 的适用范围统一由各节开头限定；本项不再重复脚本分类或更新功能清单。

#### 20.6.14.2 SCRIPT_VERSION 声明格式与一致性（强制）

1. `SCRIPT_VERSION` 必须直接声明在独立脚本自身源文件中，不得只在 README、Release 页面、下载文件名或菜单文字中记录版本。
2. 统一使用全大写常量名 `SCRIPT_VERSION`，并以 `readonly` 声明。固定格式为一行：`readonly SCRIPT_VERSION="0.2.3"`；不得在赋值行拼接命令、调用函数或动态执行外部内容，以保证版本值明确且可被自动化工具静态解析。
3. 若简单脚本只将 `SCRIPT_VERSION` 留给版本检查工具静态读取、脚本运行时并不引用该常量，ShellCheck 可能报告 `SC2034`。此时只允许在该声明行上方添加精确、带原因的局部豁免：`# shellcheck disable=SC2034 # 供版本管理工具静态读取，脚本无需运行时展示版本。`；若脚本实际会读取该变量，则不得添加此豁免。该豁免仍须按 19.2.6 记录和审查，不得扩大为文件级或全局禁用。
4. `SCRIPT_VERSION` 必须与文件头部 `ver` 完全一致。若脚本提供 `--version` 参数或菜单版本展示，必须统一读取该常量，不得在多个函数中分别硬编码版本号；不得为声明版本常量而额外增加查询接口或交互界面。管理脚本不得提供 `version` 等 CLI 子命令。
5. 该常量表示当前脚本自身的版本，不表示 Mihomo、sing-box、Nginx 或其他被管理软件的版本。管理脚本应使用清楚区分的名称，例如 `SCRIPT_VERSION` 与 `mihomo_version`；不得共用一个含义不明的 `VERSION` 变量造成混淆。
6. 如果项目有统一的 `VERSION` 文件或其他版本元数据，必须明确唯一权威来源，并通过构建或测试验证文件头 `ver` 与 `SCRIPT_VERSION` 一致。单文件自更新脚本还必须在脚本源文件中保留静态、可解析的 `SCRIPT_VERSION`，不得依赖更新器无法访问的外部版本文件。
7. 版本常量必须放在全局常量区域、业务函数定义之前；不得放在 `main` 内部、条件分支、菜单输出代码或依赖网络结果的逻辑中。库文件按 20.6.14.1 第 5 项处理。
8. 更新脚本版本时，必须同步更新文件头 `ver`、`SCRIPT_VERSION`、版本输出（若有）、CHANGELOG 和其他权威元数据。禁止只改菜单上显示的版本号。

标准声明示例（该片段放在 2.2 规定的 Root 检查通过之后、其他业务函数定义之前；完整文件头和启动顺序不在本节重复）：

```bash
# 脚本自身版本，必须与文件头 ver 保持一致。
readonly SCRIPT_VERSION="0.2.3"

# 若本脚本管理其他软件，软件版本必须使用独立变量。
managed_software_version=""
```

具备自更新能力的管理脚本可在此基础上增加 `SCRIPT_NAME`、菜单版本显示和更新逻辑；不得因此增加 CLI 子命令。普通脚本不得为了声明 `SCRIPT_VERSION` 而被迫增加版本查询接口或交互界面。

#### 20.6.15 具备自更新能力的终端管理脚本：版本展示与更新入口（强制）

本节仅适用于按 20.6.14.1 判定确实需要并具备或正在实现脚本自更新能力的管理脚本。版本展示和更新入口必须使用现有交互式主菜单；不得增加 CLI 子命令，也不得为了套用示例强行新增 `menu()`。

1. 若终端管理型脚本提供主菜单、帮助信息或状态页，应在适当位置清晰展示管理脚本自身版本，例如：`mihomo 管理脚本 v0.2.3`。版本展示必须读取 `SCRIPT_VERSION`，不得手工写死；没有这些交互界面的脚本不必为了展示版本而新建菜单或状态页。
2. 对同时管理脚本和 Mihomo 核心程序的项目，必须把两种更新入口明确区分：`更新 Mihomo` 仅更新被管理软件；`更新管理脚本` 仅更新脚本自身。不得用含糊的“更新”同时触发两种更新。
3. 只有原本存在交互式主菜单且确实支持自更新时，才增加独立菜单项，例如 `更新管理脚本（当前版本：0.2.3）`；菜单选项与实际执行函数必须一一对应。
4. 仅在脚本确实实现自更新时，推荐将自更新函数命名为 `update_script`；函数名继续遵守全小写 `snake_case`。被管理软件更新函数应使用独立名称，例如 `update_mihomo`。没有自更新功能的脚本不得为了符合命名示例而创建空壳更新函数。
5. 更新菜单项必须先显示当前 `SCRIPT_VERSION`，再查询远程版本；查询失败必须显示明确错误，不能隐藏选项、显示空版本或假报“已是最新”。
6. 检查更新和真正安装更新应能区分。若菜单提供“检查更新”功能，该功能只能查询和比较，不得写入脚本文件、替换程序或修改用户配置。
7. 更新管理脚本不得擅自修改 Mihomo 配置、机场订阅、规则集、服务数据或被管理软件版本；除非用户明确要求同时迁移，并且迁移方案经过备份、测试和说明。

示例菜单展示（颜色变量应使用项目统一颜色管理函数，不得在业务代码中直接散布 ANSI 转义码）：

```bash
show_main_menu() {
    print_header
    printf '%s\n' "${COLOR_CYAN}  Mihomo 管理脚本版本：${SCRIPT_VERSION}${COLOR_RESET}"
    printf '%s\n' "${COLOR_CYAN}  使用说明${COLOR_RESET}"
    printf '%s\n' "    1. 重装或更新 Mihomo 时，原有机场订阅会自动保留"
    printf '%s\n' "    2. 添加订阅请用「配置管理」，勿直接编辑配置文件"
    printf '%s\n' "${COLOR_GREEN} 2${COLOR_RESET}. 更新 Mihomo 核心程序"
    printf '%s\n' "${COLOR_GREEN}12${COLOR_RESET}. 更新管理脚本（当前版本：${SCRIPT_VERSION}）"
    hr
}
```

#### 20.6.16 自更新程序必须从候选脚本中安全识别版本（强制）

本节仅适用于实际执行远程脚本更新的管理型脚本。没有自更新能力的普通脚本不需要下载候选脚本，也不需要实现候选版本解析函数。

更新器下载远程候选脚本后，必须在替换当前脚本之前，从候选文件中静态读取并验证 `SCRIPT_VERSION`。候选文件属于不可信输入，**严禁通过 `source`、`.`、`eval`、执行候选脚本或调用其函数来获取版本号**。

1. 本地当前版本来自正在运行脚本已校验的 `SCRIPT_VERSION`；候选版本必须从已下载到安全临时目录的候选文件中提取。
2. 候选文件必须且只能在**顶层全局常量区域**包含一个符合固定声明格式的 `readonly SCRIPT_VERSION="X.Y.Z"`；不得把声明放在函数、条件分支、循环、命令替换或其他运行时才会执行的代码块中。缺失、多次声明、使用 `declare` / `export` / `+=` 等替代赋值方式、赋值格式变化、命令替换、变量拼接、非法字符或不符合项目 SemVer 规则时，必须拒绝更新。静态提取器必须检查声明的唯一性、顶层位置和固定格式；仅用正则或 AWK 搜索到一行匹配文本，不足以证明它是顶层声明。静态检查不能证明脚本整体安全，仍须依赖可信来源、签名/证明和代码审查。
3. 同时静态读取候选文件头部 `ver` 字段，并确认它与候选 `SCRIPT_VERSION` 完全一致；不一致即判定为发行包元数据错误并停止。
4. 候选脚本的版本必须与已验证 Release Tag、Release 元数据或项目指定版本清单相符。不得仅因候选脚本自报更高版本就信任它；版本声明不能代替来源认证和摘要/签名验证。
5. 版本解析必须使用固定格式解析器，只允许读取明确声明的版本行；不得通过 `grep` 任意命中注释、CHANGELOG、帮助文本或其他文件内容来猜测版本。
6. 比较候选版本与当前版本必须调用经过测试的 SemVer 比较函数。远程较旧、版本相同或版本无法识别时，不得覆盖当前脚本。
7. 完成来源验证、摘要/签名验证、版本一致性、`bash -n` 和必要的目标环境兼容性检查后，才允许进入备份与原子替换步骤。ShellCheck、完整自动化测试和发布验收遵循第 20.6.11 节第 15 项及第 19.2 节；目标主机更新器不得把 ShellCheck 作为强制运行时依赖。
8. 替换完成后必须对安装路径上的新脚本重新静态读取版本，并确认其与目标版本一致；验证失败必须按安全流程回滚。**不得为了验证版本而以 Root 身份直接执行刚下载/替换的新脚本的 `--version` 或其他参数。** 运行时冒烟测试的隔离沙箱条件统一遵循 20.6.17 第 7 项；无法提供安全沙箱时，只进行静态验证并依赖发布 CI 的签名/制品证明，待用户下次正常启动时再执行新版本。
9. 新版本脚本必须保持原有管理数据和配置路径兼容。若需要迁移配置或数据，必须另设明确迁移流程，不得把脚本覆盖和用户数据迁移混为一个不可逆步骤。
10. 更新器必须输出当前版本、候选版本、来源、比较结果和最终结果。例如：`当前脚本版本：0.2.3`、`发现新版本：0.3.0`、`更新完成：0.2.3 -> 0.3.0`。所有值必须来自实际校验结果。

候选脚本版本静态提取函数示例（仅适用于稳定版三段式 SemVer；使用前仍须完成来源和摘要/签名验证）：

```bash
# 从未执行的候选 Bash 脚本中静态提取唯一 SCRIPT_VERSION。
# 参数：$1 表示已下载到安全临时目录的候选脚本路径。
# 输出：校验通过的 X.Y.Z 版本号。
# 返回：成功时返回 0；文件无效、声明缺失、声明重复或格式错误时返回非 0。
extract_script_version() {
    local candidate_file="${1:-}"
    local candidate_version

    if [[ -z "$candidate_file" || ! -f "$candidate_file" || -L "$candidate_file" ]]; then
        printf '[ERROR] 候选脚本文件无效。\n' >&2
        return 1
    fi

    if ! candidate_version="$(awk '
        {
            # 统计所有常见的 SCRIPT_VERSION 赋值形式，防止通过缩进、declare、export 或 += 隐藏第二次赋值。
            if ($0 ~ /(^|[^[:alnum:]_])SCRIPT_VERSION[[:space:]]*\+?=[^=]/) {
                assignment_count++
            }

            # 只接受规范的一行 readonly 字面量声明。
            if ($0 ~ /^readonly SCRIPT_VERSION=/) {
                declaration_count++

                if ($0 !~ /^readonly SCRIPT_VERSION="[0-9]+\.[0-9]+\.[0-9]+"$/) {
                    invalid_declaration = 1
                    next
                }

                version = $0
                sub(/^readonly SCRIPT_VERSION="/, "", version)
                sub(/"$/, "", version)
            }
        }
        END {
            if (assignment_count != 1 || declaration_count != 1 || invalid_declaration) {
                exit 1
            }
            print version
        }
    ' "$candidate_file")"; then
        printf '[ERROR] 候选脚本必须且只能包含一个格式正确的 SCRIPT_VERSION 声明。\n' >&2
        return 1
    fi

    printf '%s\n' "$candidate_version"
}
```

使用该函数时，还必须独立提取候选文件头部的 `ver` 字段并与函数输出比较；随后与已验证的 Release Tag 或版本清单比较。该函数只负责基础声明文本筛查和静态提取，不验证声明是否位于顶层全局常量区域，也不验证仓库身份、网络来源、签名、摘要或版本升级优先级。**不得单独把该 AWK 示例当作完整候选脚本解析器或安全验证器。** 实际更新器必须另行确认声明位于顶层全局常量区域，并且候选文件头 `ver` 与该常量、已验证的发布版本三者一致。

#### 20.6.17 管理脚本版本功能的自动化测试（按功能适用）

本节测试范围必须按脚本类型和实际功能确定：

- 所有独立、可执行 Bash 脚本：必须验证文件头 `ver` 与唯一 `readonly SCRIPT_VERSION` 格式合法且完全一致；如果脚本通过菜单展示版本，还必须验证显示值来自该常量。无需为了测试版本常量而增加网络请求、CLI 子命令或交互界面。
- 没有自更新功能的脚本：不要求实现或测试远程版本查询、候选脚本解析、下载、替换和回滚。
- 已实现或正在实现自更新的脚本：必须覆盖以下全部适用测试，不得以脚本类型为由跳过安全更新测试。

自更新管理脚本至少验证以下内容：

1. 若管理脚本在主菜单或标题中展示版本，必须确认显示值与 `SCRIPT_VERSION` 一致；版本展示不得发起网络请求。
2. 菜单中展示的版本由变量动态生成；更新 Mihomo 与更新管理脚本调用不同函数，不会互相误触发。
3. 能正确识别候选文件中的版本；缺失、重复、格式异常、恶意命令替换或版本声明与头部不一致时必须拒绝，且不能执行候选文件。
4. 候选版本高于当前版本时才可进入更新；相同版本提示无需更新；低于当前版本默认拒绝降级。
5. 候选脚本自报版本与 Release Tag、版本清单或已验证发布元数据不一致时必须拒绝。
6. 验证失败、网络故障、摘要错误、签名错误、磁盘不足、替换中断和权限错误时，当前可用脚本必须保持不变或按设计恢复备份。
7. 更新成功后，必须确认安装路径上的文件头 `ver` 与 `SCRIPT_VERSION` 一致。若需要运行时冒烟测试，只能在经过验证的容器、虚拟机或用户命名空间沙箱中执行；测试进程可以在隔离命名空间内具有 `EUID=0` 以满足入口检查，但不得拥有宿主机 Root 能力，并且必须禁用网络、移除凭据、限制文件系统写入。不得在生产主机上以 Root 身份执行刚下载或替换的候选代码。无法安全执行时，记录为“运行时冒烟测试未执行”，依赖已验证的发布 CI 证据。
8. 测试使用临时目录和 Mock 数据，不得覆盖真实安装脚本或修改生产配置；测试完成后按 19.3.1 清理一次性测试产物，并保留正式回归用例。

**管理脚本版本的最终原则：脚本必须能明确说出“我自己是什么版本”，更新器必须能在不执行远程脚本的前提下识别“候选脚本是什么版本”，并且只有在来源可信、版本匹配、制品验证通过后，才允许安全替换当前脚本。**

## 21. 安全与敏感信息

本节只保留跨模块通用的秘密管理原则；具体执行规则分别由对应章节负责：Git 忽略和提交审查见 20.1.1，日志与输出脱敏见 10.1，Root 和系统操作见第 14 节，配置加载及网络信任见第 15 节，临时敏感文件清理见第 13 节和 19.3.1。

1. 不得将密码、Token、私钥、Cookie、API Key、认证头或其他真实凭据硬编码到脚本、测试、示例和文档中。

3. 只在必要的最小范围和最短时间内持有敏感数据；发生泄露或疑似泄露时，应立即报告并建议吊销或轮换对应凭据。

不得在本节重复网络下载、TLS 校验、路径安全、Root 环境或 Git 敏感文件规则；这些规则以本节首段列出的专项章节为准。
